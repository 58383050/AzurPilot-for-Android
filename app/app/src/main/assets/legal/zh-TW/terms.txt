2. 術語定義與法律解釋規則
2.1 【本軟體系統體系定義】
本軟體採用兩層協同的本地技術架構：
  （1）第一層為執行於 Android 作業系統 Dalvik/ART 虛擬機器環境中的“宿主應用層”（App Shell），負責介面呈現、配置管理、前臺保活服務、系統許可權適配、虛擬顯示屏管理以及基於 native JNI 的幀資料捕獲和觸控指令注入；
  （2）第二層為透過 PRoot 機制直接執行在 Android 本地使用者空間內的“嵌入式 Linux 執行時環境”（Runtime），該環境包含輕量級 Ubuntu 檔案系統、Python 執行時以及上游 AzurPilot 核心自動化指令碼庫。
【通道安全】兩層之間僅透過本地迴環網路介面（127.0.0.1）建立私有通訊通道，杜絕外部未經授權的網路探測與劫持。
2.2 【PRoot 容器技術之定義】
PRoot 是一種基於 Linux ptrace 系統呼叫跟蹤與偽造機制的非特權使用者空間 chroot/mount 模擬實現。
在本軟體中，PRoot 用於在不需要 Android 系統 Root 許可權的前提下，為 Python 自動化指令碼提供完整的 GNU/Linux 動態連結庫執行環境。
【沙箱邊界】PRoot 的所有檔案讀寫和程序執行完全受限於 Android 應用自身的沙箱許可權體系，不具備突破 Android 作業系統安全隔離模型的能力。
2.3 【橋接層與原生庫（Bridge / Native Libraries）】
指存放在應用 jniLibs 目錄或 prootLibs 目錄下的動態共享連結庫（如 libbridge.so 及 PRoot 依賴的九個底層 .so 檔案）。
該層透過直接呼叫 Linux 底層系統呼叫及 Android NDK 原生圖形介面，實現以下核心功能：
  （1）虛擬顯示屏幀緩衝區（Framebuffer）的零記憶體複製讀取；
  （2）記憶體環形緩衝區資料的高效流轉與生命週期管理；
  （3）低延遲觸控手勢座標的事件注入與分發控制。
2.4 【特權後臺服務（Privileged Service）】
指本軟體為了實現在不遮擋使用者前臺正常使用螢幕的情況下後臺執行遊戲，透過 Shizuku 框架或系統超級使用者（Root）授權啟動的 app_process 獨立後臺程序。
該程序具備與 Android 系統底層互動的合法許可權，負責動態向系統申請建立非預設的獨立虛擬顯示屏（Virtual Display），並在該虛擬屏上透過系統級介面啟動目標遊戲與注入操作。
【許可權約束】特權服務僅用於虛擬顯示屏建立與輸入注入，不執行任何越權篡改系統的惡意操作。
2.5 【自動化任務（Task）】
指由使用者在 WebUI 或本地配置中選定、並由本軟體自動執行的一系列有序螢幕操作指令集合。其支援的具體業務模組包括但不限於：
  （1）主線關卡出擊與常規海域戰鬥；
  （2）每日困難關卡挑戰與限定圖紙掃蕩；
  （3）大型作戰海域探索、要塞攻堅與港口巡迴；
  （4）演習對手對戰與戰術競技衝榜；
  （5）軍事委託任務派遣與收益領取；
  （6）戰術學院技能學習與教材匹配；
  （7）後宅艦船撫慰、存糧補充與好感度維護；

2.6 【影象模式匹配與 OCR 識別】
指本軟體利用 OpenCV 開源計算機視覺庫對螢幕截圖中的畫素矩陣進行模板相似度計算（如採用 cv::matchTemplate 函式計算歸一化相關係數），以及利用 LiteRT 輕量級神經網路推理框架執行的光學字元識別技術。
該技術用於從當前遊戲畫面中定位特定按鈕圖示、提取文字資訊並判定當前遊戲所處的狀態機節點，屬於純客戶端本地模式識別。

9. 影象模式識別、演算法容錯與介面動態變化風險
9.1 【計算機視覺與畫素比對侷限性】
本軟體底層依賴的 OpenCV 模板匹配與卷積影象識別演算法，本質上是在二維畫素色彩空間內進行的相似度機率統計運算。

  （2）螢幕物理挖孔與異形形態：包括挖孔屏、水滴屏、藥丸屏、劉海屏及大圓角曲面屏等物理開孔佈局；
  （3）系統黑邊填充機制：非標準比例螢幕上游戲引擎自動填充的黑邊（Letterboxing）或強制拉伸裁剪策略。
【位移偏差風險】儘管本軟體內建了動態視口檢測演算法，但在某些特定定製系統（如特定版本的 MIUI、OriginOS、ColorOS、HyperOS）下，系統安全區域（DisplayCutout）與黑邊邊界計算可能發生偏移，導致軟體計算出的觸控座標整體發生數個至數十個畫素的物理位移，進而點中錯誤區域，使用者知悉並自行承擔該等適配風險。

11. 裝置硬體物理負荷、電池損耗與系統穩定性責任
11.1 【CPU/GPU 高頻計算與發熱降頻】
本軟體在執行自動化任務時，需長期調動移動裝置的多核 CPU 執行 Python 直譯器、OpenCV 影象矩陣運算、LiteRT 神經網路推理，並呼叫 GPU 實施影象渲染和螢幕緩衝區合成。
這種高頻密集的本地平行計算必然導致移動終端的 SoC 核心溫度顯著上升。在夏季高溫或散熱受限的環境下，裝置將觸發 Linux 底層 Thermal 驅動的溫控節流機制（Thermal Throttling），強制降低 CPU/GPU 核心執行頻率，進而造成系統整體執行卡頓、幀率急劇暴跌。
【物理規律免責】使用者知悉發熱降頻系移動晶片的物理客觀規律，維護團隊對由此造成的遊戲掉幀或卡死概不負責。
11.2 【鋰電池加速老化與鼓包安全預警】
【重點安全預警】持續數小時乃至數十小時不間斷執行本軟體，伴隨高負荷能耗，會導致裝置鋰離子電池承受極高的迴圈充放電壓力。
若使用者在邊充邊玩的極端狀態下執行本軟體，高溫與高電壓的雙重疊加將急劇加速電解液分解與正負極材料衰退，導致電池可用實際容量嚴重縮減、電池健康度斷崖式下跌，甚至在極端劣質電池或老化電池上引發電池膨脹、鼓包、漏液或起火爆炸等嚴重硬體安全事故。
使用者有義務定期檢查電池健康狀態，維護團隊對任何電池損耗或安全事故免除一切賠償責任。
11.3 【OLED 螢幕自發光畫素燒屏與殘影免責】
當前主流智慧手機廣泛採用 AMOLED / OLED 等有機自發光顯示屏。在此類螢幕上，若長時間以高亮度顯示相對固定的靜態遊戲 UI 元素（如出擊血條、地圖網格、常駐按鈕邊框、底部狀態列），會導致該區域的有機發光畫素點因加速發光老化而發生發光效率不均勻衰退，最終在螢幕基板上留下永久性無法消除的影象殘影（即俗稱的“物理燒屏”）。
【燒屏免責宣告】儘管本軟體提供了息屏掛機、亮度壓暗及防燒屏微小偏移等保護機制，但不能排除因系統限制或使用者未開啟保護導致的燒屏缺陷。使用者承諾因長時間執行導致螢幕殘影或燒屏的，不得向維護團隊索賠更換螢幕費用。
11.4 【快閃記憶體介質磨損與零 Flash 防寫】
移動終端內建的 UFS / eMMC 快閃記憶體顆粒具有固定的物理擦寫壽命（P/E 週期）。若自動化程式頻繁將高幀率的螢幕截圖、影片錄影或龐大的除錯日誌密集寫入物理磁碟，會在短時間內耗盡快閃記憶體壽命導致主機板報廢。
【零 Flash 寫架構】為此，本軟體在系統架構上嚴格貫徹了“零 Flash 高頻讀寫”原則，所有影象幀流在 RAM 共享記憶體中迴圈週轉。
然而，若使用者自行配置開啟了極其詳盡的 DEBUG 級全量圖片落盤日誌，因此導致的快閃記憶體物理擦寫磨損由使用者自行承擔。
11.5 【系統記憶體溢位與 OOM Killer 殺程序】
Android 系統內建了嚴格的記憶體低記憶體殺程序守護機制（Low Memory Killer / LMK）。當系統可用實體記憶體（Free RAM）跌落至臨界水線以下時，系統將依據 oom_adj 評分強制終止後臺程序。
【系統機制說明】儘管本軟體部署了前臺通知保活、靜音音訊管道、雙程序守護等多重抗殺機制，但在多工併發或系統記憶體緊張時，本軟體或遊戲程序仍可能隨時被作業系統強行就地殺死。對於因程序被殺導致的關卡進度中斷、體力浪費或挑戰失敗，維護團隊不承擔任何形式的保證。
11.6 【電費與蜂窩移動流量資費承擔】
本軟體的持續後臺執行、網路更新、映象下載及長期線上會消耗使用者的電網電量及移動網際網路流量。
【資費自理】使用者在移動蜂窩網路（非 Wi-Fi）環境下執行時，若因自動化任務持續通訊或下載更新包而產生了超出套餐限額的高額蜂窩流量費用，該筆通訊賬單由使用者向基礎電信運營商全額自行結算，維護團隊概不承擔任何補貼或報銷。
11.7 【裝置物理損壞絕對豁免】
【絕對豁免條款】在任何情況下，對於因執行本軟體間接或直接引發的裝置主機板燒燬、晶片脫焊、觸控屏失靈、充電介面短路、外殼變形等一切硬體層面的物理損害，維護團隊均不承擔任何形式的直接賠償或連帶擔保責任。

16.1 【演習對手重新整理與軍銜積分機制】

【戰力評估侷限】本軟體內建的演習模組雖然包含對手戰力識別與戰力從低到高排序的篩選邏輯，但由於遊戲內的戰力顯示數值（Power Rating）並不能真實反映對手實際裝備的隱形反制能力（例如配備了高等級珍珠之淚、預裝填空襲、超巡重甲防空體系），自動化任務可能會選中實際戰力遠超表面數值的隱形精銳對手，從而導致演習挑戰遭遇嚴重慘敗。
16.2 【對手戰力評估演算法與勝率波動】
本軟體的對手篩選演算法僅基於公開介面提取的數字資訊與勝率經驗模型，維護團隊絕對不保證演習自動化能夠維持 100% 連勝紀錄。

為了防止演習戰敗丟失積分，部分高階玩家習慣在戰鬥失敗結算畫面出現前，透過強殺遊戲程序（即常稱的“SL 戰術退出”）以保全挑戰次數與積分。

18.1 【後宅存糧補充與非意向消耗免責】
後宅系統用於快速恢復艦船的心情值並提供被動經驗值收益。後宅存糧需要定期消耗食物道具進行補充。在食物耗盡時，本軟體會依據預設順序優先消耗普通油糧（如海油、海軍咖哩）。
【高階存糧免責】然而，若使用者在配置中勾選了允許使用高階食物（如皇家料理、滿漢全席），而此類高階食物往往具有極其珍稀的額外經驗加成百分比。若因長時間自動化執行導致使用者庫存中用於重要經驗加倍活動的大量頂級料理被全額消耗完畢的，維護團隊不承擔賠償責任。
18.2 【舒適度提升與金幣/傢俱幣結算】
後宅舒適度決定了經驗獲取的基礎速率。後宅傢俱購買通常需要消耗傢俱幣或鑽石。
【傢俱購買隔離】維護團隊承諾本軟體不內建任何自動購買新傢俱的功能。因使用者自身在後宅介面中的人工誤觸購買導致的傢俱幣或鑽石損失，與維護團隊無關。
18.3 【休息艦船更替與好感度積累】
後宅休息位是積累艦船好感度（觸發愛心氣泡）、恢復紅臉心情的關鍵。本軟體支援定時檢測心情並在心情回滿後輪換出戰。
【收益偏差說明】但若因影象識別延遲未能在艦船心情完全恢復的第一時間將其換入出擊艦隊，導致自動化出擊任務在艦船處於綠臉/黃臉心情的非最高收益加成狀態下開戰的，此種微小收益偏差不構成軟體缺陷。
18.4 【指揮喵買貓、洗貓與天賦重置風險】
指揮喵系統具有極高的隨機性與賭博機制。購買頂級指揮喵箱、為高稀有度指揮喵洗點重置天賦技能（俗稱“洗貓”）需要消耗海量的金幣與經驗道具。
【重點警示：洗貓極高風險】本軟體強烈建議使用者切勿開啟任何指揮喵全自動化天賦洗練功能。由於演算法難以完全衡量複雜詞條組合的主觀價值，若自動化程式在洗練過程中洗掉了極其罕見的“一發入魂”、“火之誓約”、“風之奇蹟”等彩頂級神級天賦詞條，並覆寫為普通詞條的，該等無法估量的精神與遊戲資產損失，完全由使用者自行承擔，維護團隊免責。
18.5 【指揮喵經驗餵養與珍稀喵幼崽誤合成】
在指揮喵強化升級過程中，需要將低階幼崽喵作為狗糧消耗餵養。
【狗糧合成自負】若使用者未在遊戲內嚴格鎖定具有優良初始詞條的 SR/SSR 珍稀指揮喵，導致該等極品貓苗被自動化程式誤判定為垃圾狗糧並全額合成吞噬的，由此造成的重大不可逆損失，由使用者自行承擔責任。

19. 大型作戰與海域探索自動化模組操作規範
19.1 【大世界行動力與塞壬警報值管理】
大型作戰（俗稱“大世界”）是高強度消耗行動力（AP 體力）、產出核心科研兵裝材料與大世界貨幣（塞壬特裝代幣）的複雜沙盤探索玩法。大世界的海域危險度與警報值直接影響敵艦攻防數值。
【大世界大破懲罰】在自動化執行大世界塞壬要塞、深淵海域或隱秘海域任務時，若使用者艦隊練度不足以抗衡高警報值下的敵方精英塞壬狂暴技能，可能遭遇全隊覆沒。大世界艦隊全員進入“大破損毀”狀態後，戰力將遭受高達 60% 的鉅額削弱懲罰。使用者必須提前準備足額的戰地維修工具箱，因艦隊持續受損導致任務失敗的，後果自負。
19.2 【深淵海域與要塞作戰極端強度要求】
深淵海域 5 級、6 級強度的塞壬執行者 Boss 擁有極其恐怖的護盾轉換機制、回血機制與狂暴全屏彈幕。此種極高強度的首領戰對隊伍的屬性剋制、潛艇召喚時機、手操空襲消彈有著決定性依賴。
【極難首領戰侷限】本軟體基於固定時序與自動戰鬥的邏輯在迎戰此類極高難度 Boss 時勝率存在天然上限。因自動化連續挑戰失敗導致行動力被大量白白扣除且未通關的，屬於正常遊戲機制難度範疇，維護團隊不予補償。
19.3 【港口補給購買與塞壬座標記錄儀】
各大世界港口（如紐約港、利物浦港、直布羅陀港、聖彼得堡港）每月會重新整理限定數量的高階海域座標記錄儀、高效作戰指令書及定向藍圖。本軟體包含港口巡迴購買邏輯。
【月度清空港口免責】若因港口貨幣（代幣一型/代幣二型）不足，或者由於任務引數設定錯漏未能搶在每月最後一天 23:59 的全服大世界月度重置前掃空港口核心商品，導致未使用的代幣在月末被遊戲系統強制全額按低廉比例折算為普通油糧的，該等遊戲結算機制由遊戲運營商全權制定，使用者自願承擔此類折算損失。
19.4 【信標·META 戰鬥挑戰與同步值獲取】
大世界每日產出的 META 信標（灰燼信標作戰）是獲取限定 META 角色與強化材料的關鍵。信標戰鬥每日具有助戰次數與自身挑戰次數限制。本軟體支援自動發起信標挑戰與自動申請公會助戰。
【信標助戰侷限】若因外部網路延遲導致助戰請求未能成功廣播，使得單次信標挑戰因缺乏火力支援未能擊破高階 Boss、進而導致單日 META 同步值獲取未達上限的，維護團隊不承擔技術擔保責任。
19.5 【月度重置結算與代幣清空機制】
大世界系統在每月第一天凌晨由遊戲伺服器執行硬重置，海域所有未使用的座標道具、臨時行動力包、未領取的壓制獎勵將被全額回收清空。
【月末重置自負】使用者知曉月度重置的不可逆性，應當合理安排在本月倒數第二日前完成大世界全部海域探索，切勿將全量清圖任務堆積至月末最後數小時交由自動化執行，因時間不足導致未來得及完成清剿的大世界資產損失由使用者自負。
19.6 【艦隊損壞維修與士氣低落作戰懲罰】
在大世界連續跨海域長途遠征時，艦船由於持續戰鬥環境壓力可能產生士氣低落、異常狀態感染等負面 Debuff。本軟體嘗試在港口執行自動修復與狀態解除。
【損毀懲罰自理】若因使用者大世界維修包庫存耗盡導致修復失敗，本軟體在持續殘血狀態下強行執行出擊導致全軍覆沒的，損失由使用者承擔。

20. 軍部科研室研發與藍圖解析模組操作規範
20.1 【科研專案優先順序佇列排程演算法】
軍部科研室是玩家消耗資源獲取高階科研期數艦船圖紙、限定彩皮裝備設計圖紙的最重要日常模組。本軟體內建了一套高度複雜的基於期數優先順序、消耗收益比權重的動態排程演算法。
【PRNG 隨機性說明】然而，由於科研專案重新整理完全由遊戲伺服器端以機率偽隨機數（PRNG）演算法生成，在連續數天乃至數週無法重新整理出頂級“天運擬合”、“特定彩圖紙研發”專案時，演算法只能依據降級規則選擇價效比較低的普通基礎科研專案。使用者知曉科研專案重新整理的機率隨機性，不得將科研藍圖產出未達預期歸咎於本軟體。
20.2 【耗費魔方/金幣科研專案的風險防範】
科研專案中存在極其特殊的“魔方研究定向”任務（例如短時間內消耗 3 枚魔方或 10 枚魔方獲取海量定向藍圖）。該類專案雖然具有極高的藍圖收益，但對心智魔方庫存具有極強的侵蝕性。
【魔方科研高危警示】維護團隊在軟體底層預設了魔方科研的全域性安全鎖定。若使用者在知情或不知情的狀態下自行解鎖了該類高風險任務的排程許可權，導致短期內消耗了數百枚心智魔方，直接摧毀了其後續抽卡造船儲備的，該等因非理性操作授權引發的慘重損失，完全由使用者自行買單，維護團隊依法完全免除賠償義務。
20.3 【心智解析藍圖轉化與命運擬合機制】
當某一科研期數的艦船達到滿破 30 級開發等級後，溢位的藍圖可在遊戲內轉化為通用原型點數或用於命運擬合（Fate Simulation）。
【藍圖處分人工原則】本軟體不負責執行具有不可逆財產處分性質的“藍圖批次回收分解為原型點數”操作。一切涉及藍圖銷燬、轉化、原型商店兌換的重大資產處分行為，使用者必須親自在遊戲客戶端內人工手動核對並操作。
20.4 【科研裝備研發材料合成與消耗不可逆】
裝備研發系統（裝備工坊）需要將大量低階裝備作為基礎胚子，並消耗海量的高階軍械材料、超合金、電子元件將其逐級晉升合成為極其珍稀的 +10、+13 頂級畢業裝備。
【裝備合成紅線】本軟體絕對禁止自動代使用者執行任何裝備工坊內的不可逆最終合成操作。因使用者自己在遊戲內操作失誤誤合成了錯誤裝備的，與本軟體無關。
20.5 【科研期數切換與研發點數損失免責】
在遊戲開放全新科研期數時，使用者需要在舊期數與新期數之間做出資源傾斜抉擇。
【期數選擇自負】若使用者在配置中錯誤指定了追趕期數，導致自動化系統持續向早已滿破畢業的陳舊期數傾倒科研資源、白白浪費了數個月研發時間與數千萬金幣資源的，該等戰略決策失誤屬於使用者個人的認知偏差，維護團隊不承擔任何指導過失責任。

各區服的遊戲停服維護時間完全不同（例如國服通常在每週四上午，日服通常在每週四下午，美服在週四夜間，且跨時區夏令時切換會導致維護時鐘動態位移）。
【跨時區維護風險自負】本軟體內建的定時任務排程器完全依附於使用者本地裝置的系統時間。若使用者跨時區配置錯誤導致自動化任務在遊戲伺服器處於停機維護期間強行啟動並持續傳送請求的，風險由使用者自負。
27.8 【多賬號與多伺服器切換資料汙染】
部分高階使用者在一臺裝置上同時安裝了多個不同區服的遊戲客戶端，或透過分身多開功能登入了多個賬號。
【多賬號混淆自負】使用者在切換執行環境時，有嚴格的責任核實當前啟用的任務配置是否與當前登入的目標遊戲賬號準確匹配。因配置串聯混淆導致將主號的消耗策略錯用在小號、或將小號的退役策略錯施於大號核心資產的，維護團隊依法免除一切賠償責任。

28. 虛擬顯示屏（Virtual Display）底層架構、多視窗併發與防凍結機制
28.1 【虛擬顯示屏技術架構與工程實現】
為了實現讓使用者在手機前臺正常瀏覽網頁、微信聊天、觀看影片的同時，後臺獨立執行遊戲自動化任務的高階使用者體驗，本軟體透過特權程序（基於 Shizuku 或系統超級使用者 Root 呼叫的 app_process）直接向 Android 作業系統的底層 DisplayManagerService 發起通訊，利用系統隱藏 API（createVirtualDisplay）在實體記憶體中動態構建一塊完全獨立的第二虛擬螢幕（Virtual Display）。
【技術架構原理】該虛擬屏擁有獨立的物理解析度、螢幕畫素密度（DPI）、色彩空間格式（RGBA_8888）以及獨立的視窗合成圖層（Layer Stack）。
28.2 【虛擬螢幕輸入與影象管道】
在虛擬螢幕架構下，Android 系統將目標遊戲客戶端的全部視窗和圖形渲染完全重定向至該虛擬顯示層中。
【無感輸入管道】原生橋接層（Native Bridge）透過基於 C++17 開發的高效能管道，直接掛接虛擬屏的 ImageReader / Surface 幀緩衝區，實現零複製記憶體共享；同時，特權服務利用 InputManager 將所有的觸控手勢精準定位並派發至該虛擬屏的獨立座標空間中，完全不干擾使用者在主物理螢幕上的正常人機互動。
28.3 【ROM 廠商後臺凍結（Freezer）機制之衝突】
現代移動作業系統為了極致壓縮功耗並延長續航，在底層部署了極其嚴苛的系統凍結機制（如 Linux Cgroup Freezer、MIUI/HyperOS 效能引擎、OriginOS 記憶體壓縮策略）。
【廠商後臺凍結原理】當一個應用被推入非主物理屏、或者主屏熄滅超過一定時長後，廠商的省電守護程序會強行將遊戲程序及虛擬螢幕關聯的 Activity 掛入掛起凍結狀態，徹底剝奪其 CPU 時間片，導致遊戲畫面完全停滯、OpenGL 渲染指令停止提交、觸控事件排隊堆積。
28.4 【AppWatchdog 踢活機制與技術侷限】
為了對抗廠商激進的後臺凍結策略，本軟體內建了專門的“應用看門狗”（AppWatchdog）機制。該看門狗透過週期性輪詢虛擬螢幕頂級視窗包名、監測幀緩衝區更新時間戳，一旦發現遊戲發生幀停滯（Frame Freeze），便會嘗試透過底層 IPC 喚醒機制向系統提交輕量級喚醒脈衝、重新整理虛擬屏 Surface 配置，迫使廠商 Freezer 釋放凍結鎖。
【看門狗踢活侷限性】然而，使用者必須深刻理解：廠商的定製 ROM 存在數十種各不相同的私有休眠邏輯，維護團隊絕對不保證看門狗踢活機制能夠在所有廠商的每一個系統版本中 100% 成功阻止遊戲被凍結。
28.5 【鎖屏狀態下虛擬屏幀停滯與息屏休眠】
在使用者按下手機電源鍵鎖屏後，Android 系統預設會關閉主物理顯示屏並向所有關聯 Display 發出螢幕關閉廣播。此時，硬體 GPU 通常會進入深度低功耗休眠，虛擬屏的幀率可能瞬間由 60fps 跌落至 0fps。
【息屏休眠應對建議】儘管本軟體提供了息屏掛機服務，但在某些廠商系統（如未解除深度睡眠策略的機型）中，鎖屏將直接導致自動化任務徹底失去視覺反饋。使用者若需要在鎖屏狀態下持續執行，有責任根據官方教程在系統開發者選項中開啟“充電不鎖屏”或在電池管理中將遊戲與本軟體徹底加入“無限制白名單”。
28.6 【虛擬屏解析度強制拉伸與變形失真】
為確保影象識別的高精度，本軟體通常會將虛擬顯示屏的標準解析度嚴格鎖定為 1280x720 或 1920x1080 標準 16:9 比例。
【標準解析度鎖定】若使用者系統開啟了某些廠商特有的“全域性自由視窗拉伸”、“應用寬高比強制填滿”功能，可能導致遊戲客戶端在虛擬螢幕內部強行發生拉伸畸變，進而徹底破壞基於模板的影象識別準度，該類失真故障由使用者自行排除。
28.7 【多視窗併發導致的系統資源飢渴】
在虛擬屏與主屏同時執行的高併發場景下，移動裝置的硬體編解碼器、GPU 視訊記憶體頻寬、系統實體記憶體（RAM）承受雙倍負荷。
【硬體資源飢渴預警】對於實體記憶體小於等於 8GB 的中低端裝置，主前臺應用的高畫質影片播放或 3D 遊戲執行極易引發系統級記憶體嚴重吃緊，進而導致虛擬屏後側的遊戲程序被 LMK 閃電處決。使用者知悉併發多開的硬體效能門檻，不以此類資源搶佔崩潰向維護團隊歸責。
28.8 【多程序通訊故障與僵死程序殘留】
特權後臺服務跨程序執行，涉及複雜的 Binder 通訊、Socket 套接字以及 Unix Domain Socket 本地管道。
【僵死程序清理建議】當宿主應用發生異常被系統強殺後，底層的 app_process 或 PRoot 守護程序可能在極罕見情況下形成僵死殘留，繼續佔據特定本地埠。若使用者遇到“埠被佔用”、“特權服務無法重連”報錯，使用者應當透過應用內建的“強制停止全部後臺守護”按鈕或直接重啟手機來徹底重置執行時狀態。

29. 資料災備、配置遷移、雲備份與版本平滑升級規範
29.1 【資料架構與儲存分佈全景認知】
本軟體在執行過程中產生的資料資產嚴格區分為三類：
  （1）輕量級偏好配置：包括介面主題偏好、語言選擇、任務排程開關、定時觸發策略等，由 Jetpack DataStore 以基於 Proto/Preferences 的本地二進位制檔案儲存；
  （2）核心業務執行配置：包括各任務的關卡選擇、艦隊優先順序、資源購買閾值等，由上游核心以 YAML / JSON 格式持久化於本地私有應用沙箱目錄；
  （3）龐大的執行時環境映象與日誌：包括解壓後的 Ubuntu PRoot 檔案系統樹（包含數萬個 Linux 系統檔案）、以及滾動輪換的執行除錯日誌（logs 目錄）。
29.2 【敏感憑證排除系統雲備份機制】
依據《中華人民共和國個人資訊保護法》對敏感個人資訊的保護要求，為了防止使用者的無線除錯配對金鑰（Adb Key）、私有鑑權 Token 等敏感安全憑證隨系統雲備份被同步上傳至各大廠商的雲端備份伺服器，本軟體在工程配置上透過 res/xml/backup_rules.xml 及 res/xml/data_extraction_rules.xml 進行了極其嚴格的雲備份顯式排除宣告。
【雲備份顯式排除】使用者在更換新手機、使用廠商提供的“一鍵換機”或“雲端整機恢復”功能後，上述高敏感安全憑證不會被自動遷移。使用者必須在新裝置上重新進行首次嚮導授權與配對流程。
29.3 【跨版本升級與配置平滑遷移】
維護團隊在釋出軟體新版本時，會竭力提供向前相容的資料庫與配置遷移邏輯（Schema Migration）。
【大版本架構變更說明】然而，當軟體架構發生代際級別的根本性重構（例如配置體系升級、底層演算法邏輯重寫）時，新版本軟體可能無法無縫繼承極老舊歷史版本的自定義配置。在此類特殊大版本升級場景下，系統可能會重置部分不相容的引數項至預設安全值。使用者有義務在新版本更新發布後，仔細核驗關鍵任務配置的有效性。
29.4 【Rootfs 執行環境熱更新與全量重灌】
本軟體的更新分為兩條獨立技術鏈路：第一條為 Android 宿主 APK 安裝包更新，第二條為 PRoot 執行時環境與 Python 指令碼庫的熱更新。
【雙鏈路更新機制】若使用者在熱更新過程中遭遇突發網路斷流導致檔案寫入殘缺損壞，或者由於 Python 位元組碼快取（__pycache__）與新程式碼發生髒資料衝突引發持續報錯，使用者應當透過設定頁中的“重新部署執行時環境”功能執行全量重灌覆蓋，以恢復純淨健康的基線映象。
29.5 【使用者離線資料主動備份義務】
本軟體屬於本地執行工具，維護團隊不為使用者提供任何雲端同步或雲端災備託管服務。
【離線主動備份義務】使用者對自身辛勤配置的複雜任務流程、個性化出擊方案、歷史執行資料負有完全且獨立的資料備份義務。使用者應當定期使用應用內的“配置匯出”功能將配置打包儲存至外部儲存卡或私人安全網盤中。因裝置硬體損壞、系統刷機格機、誤清儲存空間導致所有配置付之一炬的，損失全部由使用者自行買單。
29.6 【快取與無用歷史日誌的手動清理】
本軟體的日誌系統雖然部署了自動輪換機制，但在長期超高頻執行任務後，歷史壓縮日誌包與影象快取可能累積佔用數百兆位元組的磁碟空間。
【磁碟空間清理指引】儲存空間極其緊張的使用者，應當養成定期進入軟體設定頁面點選“清理歷史快取與日誌”的習慣，以釋放快閃記憶體空間、保障宿主系統順暢運轉。
29.7 【跨平臺與模擬器環境遷移適配】
部分使用者嘗試將手機端匯出的配置直接匯入 PC 端的 Android 模擬器（如 MuMu 模擬器、雷電模擬器、藍疊模擬器）或不同架構的裝置（如 x86_64 架構裝置）。
【模擬器架構適配免責】由於移動端與 PC 模擬器在底層圖形渲染引擎、觸控事件上報協議、螢幕 DPI 縮放規則上存在微妙差異，直接跨架構套用移動端配置可能導致點選座標發生微小系統性偏位。使用者在跨裝置遷移配置後，必須在人工監視下重新校準座標基準。
29.8 【解除安裝即徹底銷燬之法律確認】
當使用者決定不再使用本軟體並在系統桌面長按圖示執行“解除安裝”操作時，Android 系統的 Linux 沙箱底層會自動且不可逆地抹去屬於本軟體私有資料目錄下的所有檔案（包括解壓的 Ubuntu PRoot 容器、所有的 Python 程式碼、全部的使用者配置檔案與本地日誌）。

反作弊安全中心在服務端會對客戶端上報的每一個網路資料包到達間隔（Packet Inter-Arrival Time）以及關卡內每個指令的時間戳（Timestamp）展開離散傅立葉變換（DFT）或功率譜密度分析。
【傅立葉分析風控】若使用者連續數日以高度相似的節律、在完全固定的秒數區間內週而復始地傳送出擊戰鬥指令，時序訊號在頻域上必然會暴露出人工指令碼特有的週期性尖峰（Harmonics）。此類基於訊號處理的頻域特徵檢測完全超越了客戶端單純的時間隨機抖動能力，使用者知悉長期掛機必然觸發頻域反作弊審查。

在主線大地圖與大型作戰探索中，網格尋路演算法（如 A* 尋路）傾向於計算出幾何意義上的最短路徑或最優路徑。

32. 跨平臺執行容器化隔離、底層系統呼叫攔截與安全沙箱深度技術規約
32.1 【PRoot Ptrace 系統呼叫攔截與重定向工程原理】
本軟體之所以能夠在不需要 Android 系統 Root 超級許可權的前提下，在普通使用者空間完整執行 Ubuntu Linux 環境，完全仰賴於 Linux 核心提供的 ptrace（Process Trace）除錯系統呼叫與 seccomp（Secure Computing Mode）安全沙箱機制。
【Ptrace使用者空間模擬原理】當容器內的 Python 直譯器或二進位制動態庫發起例如 open()、execve()、stat()、chroot() 等檔案系統與程序控制系統呼叫時，PRoot 監控程序會攔截該系統呼叫，將其訪問的路徑（如 /usr/bin/python3、/etc/ld.so.conf）在使用者空間實時動態重定向翻譯為 Android 應用私有資料目錄下的實際物理路徑（如 /data/data/com.azurpilot.ghio/files/rootfs/...）。此種基於攔截模擬的技術架構屬於純粹的使用者空間模擬，完全遵從作業系統底層安全策略。
32.2 【SELinux 策略與非特權沙箱安全邊界】
Android 移動作業系統內建了由美國國家安全域性主導設計的極其嚴苛的增強型安全 Linux 策略（Security-Enhanced Linux, SELinux）。
【SELinux沙箱強隔離保證】本軟體的宿主應用及 PRoot 容器均被嚴格禁錮在系統分配的獨立應用級別 SELinux 上下文沙箱（如 u:r:untrusted_app:s0:c...）之中。這意味著，本軟體在物理上絕對沒有任何可能越權訪問其他第三方應用（如微信、支付寶、網銀、遊戲自身）的私有沙箱目錄，絕對無法讀取系統中其他應用的資料庫檔案。本軟體的全部資料讀寫與程序衍生均完全閉環在自身的一畝三分地之內，具備極高的本地安全純淨性。
32.3 【Native JNI 橋接層與圖形緩衝區直接訪問機制】
為了徹底擺脫傳統投屏方案高延遲、高 CPU 佔用的工程死結，本軟體的 Native 橋接層（C++17 實現）透過 NDK 原生圖形介面（如 AImageReader、ANativeWindow）直接與底層 SurfaceFlinger 渲染管線掛接。
【零複製高效能管道】橋接層透過將虛擬顯示屏輸出的硬體圖形緩衝區（GraphicBuffer）對映至共享記憶體環形佇列，實現了影象幀資料的“零記憶體複製”（Zero-Copy）跨程序排程，使 Python 執行時能夠在數毫秒內獲取到未經壓縮的原始 RGBA 幀矩陣。此種高效通訊機制完全遵循 Android 開放圖形框架，不存在任何對圖形驅動實施越權掛鉤的惡意行為。
32.4 【多架構二進位制動態連結與 ABI 相容性矩陣】
現代 Android 智慧移動裝置主要基於 64 位 ARM 處理器架構（ARM64-v8a / AArch64），部分 Android PC、車載中控或開發平板則基於 x86_64 處理器架構。
【多架構ABI相容矩陣】為了確保在不同 CPU 架構上的穩定部署，本軟體的 PRoot 容器及全部 C/C++ 共享動態庫均針對目標 ABI 進行了雙重獨立交叉編譯與連結最佳化。使用者在下載安裝時，應用會自動檢測底層 CPU 架構並拉取與其硬體原生指令集 100% 匹配的專用 Rootfs 執行時映象，杜絕跨架構動態翻譯（如二進位制指令轉譯導致的嚴重效能損耗與記憶體崩潰）。
32.5 【Android 14/15 目標 SDK 35+ 記憶體執行許可權限制】
在針對 Android 14（API 34）、Android 15（API 35）及更高版本系統的演進適配中，Google 引入了極其激進的 W^X（Write XOR Execute）安全記憶體保護機制，強制禁止應用在具有可寫許可權的內部私有儲存目錄（如 /data/data/...）中直接透過 execve() 載入並執行未受信任的 ELF 原生二進位制可執行檔案。
【現代Android高版本安全演進】為此，本軟體在底層技術路徑上進行了顛覆性的合規重構：所有 PRoot 核心可執行元件及底層 Linux 系統動態庫均經過合規封裝與靜態命名，放置於應用 APK 的原生本地庫目錄（jniLibs / prootLibs）中，由 Android 官方 Package Manager 在安裝時依法提取至專屬的只讀 native 目錄。該設計完全遵循 Android 現代安全框架最新規範，不存在任何違規程式碼注入風險。
