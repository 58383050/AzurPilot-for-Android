2. Term definitions and legal interpretation rules
2.1 [Definition of this software system system]
This software adopts a two-layer collaborative local technology architecture:
  (1) The first layer is the "host application layer" (App Shell) running in the Dalvik/ART virtual machine environment of the Android operating system, which is responsible for interface presentation, configuration management, front-end keep-alive services, system permission adaptation, virtual display management, and native JNI-based frame data capture and touch command injection;
  (2) The second layer is the "embedded Linux runtime environment" (Runtime) that runs directly in the Android local user space through the PRoot mechanism. This environment includes the lightweight Ubuntu file system, Python runtime, and the upstream AzurPilot core automation script library.
[Channel Security] A private communication channel is established between the two layers only through the local loopback network interface (127.0.0.1) to prevent unauthorized external network detection and hijacking.
2.2 [Definition of PRoot container technology]
PRoot is an unprivileged user space chroot/mount emulation implementation based on the Linux ptrace system call tracking and forgery mechanism.
In this software, PRoot is used to provide a complete GNU/Linux dynamic link library running environment for Python automation scripts without requiring Android system Root permissions.
[Sandbox Boundary] All file reading and writing and process execution of PRoot are completely limited by the sandbox permission system of the Android application itself, and it does not have the ability to break through the security isolation model of the Android operating system.
2.3 [Bridge layer and native libraries (Bridge/Native Libraries)]
Refers to the dynamic shared link library (such as libbridge.so and the nine underlying .so files that PRoot depends on) stored in the application's jniLibs directory or prootLibs directory.
This layer implements the following core functions by directly calling Linux underlying system calls and Android NDK native graphics interface:
  (1) Zero memory copy reading of the virtual display frame buffer (Framebuffer);
  (2) Efficient transfer and life cycle management of memory ring buffer data;
  (3) Event injection and distribution control of low-latency touch gesture coordinates.
2.4 [Privileged Service]
Refers to the app_process independent background process that this software starts through the Shizuku framework or the system superuser (Root) authorization to run the game in the background without blocking the user's normal use of the screen in the foreground.
This process has the legal authority to interact with the bottom layer of the Android system, and is responsible for dynamically applying to the system to create a non-default independent virtual display (Virtual Display), and launching target games and injection operations on the virtual screen through the system-level interface.
[Permission Constraints] Privileged services are only used for virtual display creation and input injection, and do not perform any malicious operations to tamper with the system beyond authority.
2.5 [Automation Task (Task)]
Refers to a series of ordered screen operation instructions selected by the user in the WebUI or local configuration and automatically executed by the software. The specific business modules it supports include but are not limited to:
  (1) Attack in the main line level and fight in conventional sea areas;
  (2) Daily difficult level challenges and limited drawing sweeps;
  (3) Large-scale combat sea area exploration, fortress attack and port patrol;
  (4) Practice opponent battles and tactical competitions to climb the rankings;
  (5) Dispatch of military entrusted tasks and receipt of income;
  (6) Tactics Academy skill learning and teaching materials match;
  (7) Home ship comfort, food storage replenishment and favorability maintenance;
  (8) Blueprint analysis and project research and development of the Military Research Office.
2.6 [Image pattern matching and OCR recognition]
This software uses the OpenCV open source computer vision library to perform template similarity calculation on the pixel matrix in the screenshot (such as using the cv::matchTemplate function to calculate the normalized correlation coefficient), and uses the LiteRT lightweight neural network inference framework to perform optical character recognition technology.
This technology is used to locate specific button icons from the current game screen, extract text information, and determine the state machine node of the current game. It is a pure client-side local pattern recognition.

28. Virtual Display underlying architecture, multi-window concurrency and anti-freezing mechanism
28.1 [Virtual display technology architecture and engineering implementation]
In order to achieve an advanced user experience that allows users to browse web pages, chat on WeChat, and watch videos normally in the foreground of the mobile phone while running game automation tasks independently in the background, this software directly initiates communication to the underlying DisplayManagerService of the Android operating system through a privileged process (based on app_process called by Shizuku or the system superuser Root), and uses the system's hidden API (createVirtualDisplay) to dynamically build a completely independent second virtual screen (Virtual Display) in the physical memory.
[Technical Architecture Principle] The virtual screen has independent physical resolution, screen pixel density (DPI), color space format (RGBA_8888), and independent window composition layer (Layer Stack).
28.2 [Virtual screen input and image pipeline]
Under the virtual screen architecture, the Android system completely redirects all windows and graphics rendering of the target game client into the virtual display layer.
[Senseless Input Pipeline] The native bridge layer (Native Bridge) directly connects to the ImageReader / Surface frame buffer of the virtual screen through a high-performance pipeline developed based on C++17 to achieve zero-copy memory sharing; at the same time, the privileged service uses the InputManager to accurately locate and dispatch all touch gestures to the independent coordinate space of the virtual screen, without interfering with the user's normal human-computer interaction on the main physical screen.
28.3 [Conflict between ROM manufacturers’ background freezing (Freezer) mechanism]
In order to extremely reduce power consumption and extend battery life, modern mobile operating systems deploy extremely strict system freezing mechanisms (such as Linux Cgroup Freezer, MIUI/HyperOS performance engine, and OriginOS memory compression strategy) at the bottom layer.
[Manufacturer background freezing principle] When an application is pushed to a non-main physical screen, or the main screen is turned off for more than a certain period of time, the manufacturer's power-saving daemon will force the game process and the activities associated with the virtual screen to be suspended and frozen, completely depriving them of CPU time slices, causing the game screen to completely stagnate, OpenGL rendering instructions to stop submitting, and touch event queues to accumulate.
28.4 [AppWatchdog kick-out mechanism and technical limitations]
In order to combat the aggressive background freezing strategy of manufacturers, this software has a built-in special "AppWatchdog" mechanism. The watchdog periodically polls the virtual screen's top-level window package name and monitors the frame buffer update timestamp. Once it finds that the game has frame freeze (Frame Freeze), it will try to submit a lightweight wake-up pulse to the system through the underlying IPC wake-up mechanism, refresh the virtual screen Surface configuration, and force the manufacturer Freezer to release the freeze lock.
[Limitations of watchdog kicking] However, users must have a deep understanding: there are dozens of different private hibernation logics in manufacturers’ customized ROMs, and the Maintainers absolutely cannot guarantee that the watchdog kicking mechanism can 100% successfully prevent the game from being frozen in every system version from all manufacturers.
28.5 [Virtual screen frame stagnation and screen sleep in locked screen state]
After the user presses the phone's power button to lock the screen, the Android system will turn off the main physical display by default and send a screen off broadcast to all associated Displays. At this time, the hardware GPU usually enters deep low-power sleep, and the frame rate of the virtual screen may drop from 60fps to 0fps in an instant.
[Recommendations for dealing with screen-free hibernation] Although this software provides a screen-free and hang-up service, in some manufacturers' systems (such as models that do not release the deep sleep policy), locking the screen will directly cause the complete loss of visual feedback for automated tasks. If the user needs to continue running with the screen locked, it is the user's responsibility to turn on "charging without locking the screen" in the system developer options according to the official tutorial or to completely add the game and this software to the "unrestricted whitelist" in the battery management.
28.6 [Forced stretching and deformation distortion of virtual screen resolution]
To ensure high accuracy of image recognition, this software usually strictly locks the standard resolution of the virtual display to 1280x720 or 1920x1080 standard 16:9 ratio.
[Standard Resolution Lock] If the user system turns on the "Global Free Window Stretch" and "Application Aspect Ratio Forced Fill" functions unique to some manufacturers, it may cause the game client to force stretching distortion inside the virtual screen, thereby completely destroying the accuracy of template-based image recognition. Such distortion faults must be eliminated by the user.
28.7 [System resource hunger caused by multi-window concurrency]
In a high-concurrency scenario where the virtual screen and the main screen run simultaneously, the mobile device's hardware codec, GPU memory bandwidth, and system physical memory (RAM) bear double the load.
[Hardware Resource Hunger Warning] For low-end and mid-range devices with physical memory of 8GB or less, high-definition video playback or 3D game running in the main foreground application can easily cause serious shortage of system-level memory, which in turn causes the game process behind the virtual screen to be terminated by LMK lightning. Users are aware of the hardware performance threshold for concurrent multi-distribution and do not blame the Maintainers for such resource preemption crashes.

31. System-level automated prevention and detection technology boundaries, clarification of misunderstandings and behavioral auditing
31.1 [Boundaries of behavioral anthropomorphism and random perturbation algorithms]
