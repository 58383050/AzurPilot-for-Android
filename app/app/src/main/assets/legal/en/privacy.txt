1. Definition of terms and classification of personal information
1.1 [Definition of personal information]
According to Article 4 of the "Personal Information Protection Law of the People's Republic of China", personal information refers to various information related to identified or identifiable natural persons recorded electronically or by other means, excluding anonymized information.
[Involving definition of data scope]:
In the context of the technical operation of this software, the categories of personal information that may be involved include but are not limited to:
  ▶ Game character nickname and numeric UID (if shown in debugging screenshots or exception troubleshooting logs);
  ▶ The underlying hardware feature identifier of the device (displayed in the troubleshooting log);
  ▶ Wireless debugging (ADB) connection key and local control password;
  ▶ Some of the text or visual information contained in automated screenshot caches may be associated with personally identifiable information.
1.2 [Definition of Sensitive Personal Information—Protection of Core Sensitive Credentials]
According to the provisions of Article 28 of the "Personal Information Protection Law of the People's Republic of China", sensitive personal information is personal information that, once leaked or illegally used, may easily cause the personal dignity of natural persons to be infringed or the personal and property safety to be endangered, including biometrics, religious beliefs, specific identities, medical health, financial accounts, whereabouts and other information, as well as the personal information of minors under the age of fourteen.
[Core Sensitive Credential Protection Scope]:
In this software, the following data is included in the highest level of protection of sensitive personal information in accordance with the law, and is physically isolated and strictly protected:
  ▶ Device lock screen fingerprint/face authentication interaction results (only one-way reception of system Boolean values, never contact with biometric raw data);
  ▶ Wireless Debugging RSA pairing private key (adbkey) and pairing authentication Token;
  ▶ LAN and remote control access password and identity verification token.
1.3 [De-identification and anonymization]
De-identification refers to the process of processing personal information so that it cannot identify a specific natural person without the help of additional information; anonymization refers to the process of processing personal information so that it cannot identify a specific natural person and cannot be restored.
[Processing principles and technical measures]:
  ▶ When generating error diagnosis logs and data export packages, this software strives to implement de-identification design and strive to erase directly readable personal sensitive attributes;
  ▶ Implement desensitization masks for possible sensitive identifiers to prevent unauthorized reverse correlation analysis.
1.4 [Local private directory and application sandbox]
Refers to the independent storage space allocated exclusively for this software by the Android operating system based on the Linux file system permission model (usually the physical path is /data/user/0/com.azurpilot.ghio/).
[Sandbox security boundary]:
  ▶ This directory is protected by the operating system kernel-level SELinux mandatory access control policy and UID/GID permission isolation;
  ▶ In the default non-root environment, any other ordinary third-party applications installed on the device are physically blocked from the outside, and it is absolutely impossible to read any files in the private directory of this software across directories.
1.5 [Embedded PRoot container environment data]
Refers to the lightweight Ubuntu Linux root file system (Rootfs) that is decompressed and resides in the software's private storage directory.
[Container environment asset composition]:
  ▶ The container environment includes independent /etc, /usr, /var directory system, Python 3 runtime library and upstream AzurPilot automation code library;
  ▶ All data and files in the container are completely private internal data of this application from the perspective of the host operating system and are completely protected by the application sandbox.
1.6 [Run Diagnostic Log and System Stack Data]
Refers to the text flow records written to the physical flash memory of the device by the Timber log framework and the Python built-in logging module during the running process of this software.
[Diagnostic log contains information]:
  ▶ System initialization timing, component startup status, and JNI bottom-level call time;
  ▶ Image template matching score, task state machine transition steps;
  ▶ Complete crash stack trace (Crash Stacktrace) when an uncaught exception occurs, used for fault location and troubleshooting.

▶ (1) Key storage security level: The RSA key pair is securely generated and stored in the application's private encryption preference directory, and its permissions are strictly protected at the Linux system file level;
  ▶ (2) Explicit physical exclusion of system cloud backup (core security defense line): In order to prevent the highly sensitive ADB debugging control key from being cloned and leaked to a third-party cloud along with the mobile phone manufacturer's system cloud backup or complete machine replacement migration, this software lists it as an absolute exclusion in the project manifest (AndroidManifest.xml and backup_rules.xml / data_extraction_rules.xml) to ensure that the key is physically isolated within the current single device.

In order to provide users with an intuitive web-based management console, this software has a built-in lightweight web server. 4. Information storage location, technical protection measures and life cycle management
4.1 [Storage location: Device local private sandbox directory]
In accordance with the legal spirit of Article 40 of the "Personal Information Protection Law of the People's Republic of China" on personal information localization and data residency, this software implements the most thorough "localization residency" principle in data life cycle management: all user preferences, configurations, operation logs, temporary images, operating environment images and key credentials generated by installing, configuring, and running this software are 100% protected. Saved in the device's internal private storage space (/data/user/0/com.azurpilot.ghio/). This software does not build any external centralized data center, and there is absolutely no background silent upload logic.
4.2 [Android system underlying sandbox isolation and access control]
This software fully relies on and deeply integrates the multi-layer defense security architecture of the Android mobile operating system:
  ▶ (1) Linux UID/GID process isolation: When the Android system installs this software, it is assigned a system-wide unique Linux user identifier (UID). At the operating system kernel level, the file system strictly limits the read and write permissions of the application private directory to the process corresponding to the exclusive UID through standard POSIX permission bits (such as 0700 / 0600). Other ordinary applications installed on the device are deprived of permission to access this directory at the kernel level;
  ▶ (2) SELinux mandatory access control policy: Even in specific multi-user environments or privilege escalation scenarios, the SELinux policy rules at the bottom of the operating system strictly stipulate the access rules of the untrusted_app domain to the file system label (Context) to prevent illegal cross-sandbox traversal;
  ▶ (3) Memory encryption and instant erasure of sensitive credentials: When processing sensitive passwords, authentication tokens and decryption keys, this software preferentially uses securely erasable character arrays (char[] / byte[]) instead of immutable strings (java.lang.String) for memory holding. It overwrites the memory area with zero values as soon as the credentials are verified, reducing the technical risk of stealing sensitive credentials by reading the memory image (Memory Dump).
4.3 [Sensitive pairing key exclusion system cloud backup mechanism - core security defense line]
  ▶ (1) Potential leakage risks of system cloud backup:
      a. Current mainstream smartphone operating systems (such as Google's native Android, Xiaomi MIUI/HyperOS, Huawei EMUI, OPPO ColorOS, etc.) generally have built-in convenient "full machine cloud backup" and "one-click machine replacement assistant" functions. When a user turns on cloud backup, the system will by default upload the shared preferences (SharedPreferences) and database in the application's private directory to the mobile phone manufacturer's public cloud server without any awareness. For common configuration items, this kind of backup helps improve the machine replacement experience;
b. However, for sensitive security credentials such as wireless debugging (ADB) pairing keys and local authentication tokens, once they are synchronized to the manufacturer's cloud with the backup, it is extremely easy for the credentials to be substantially stolen and leaked due to theft of the cloud account or cross-device transmission during the device replacement process.
  ▶ (2) Strict deployment of cloud backup isolation rules: In order to completely eliminate the above security risks, this software deploys high-level security backup rule configuration files (res/xml/backup_rules.xml and res/xml/data_extraction_rules.xml adapted to Android 12+) in the project list in accordance with the official Android security specifications. We have configured clear exclusion instructions in the rules: we explicitly exclude all file paths that store ADB pairing private keys, pairing port history, control passwords and identity tokens, and forcibly prohibit the bottom layer of the operating system from including such highly sensitive credentials into cloud backup or inter-device cloning transfer processes. After the user switches to a new mobile phone, such credentials must be securely regenerated on the new device to ensure that the old credentials will never have any traces of leakage in the network cloud.
4.4 [Zero high-frequency Flash writing and memory data protection]
The physical flash memory chip (UFS/eMMC) of mobile terminals is a physical storage medium with limited endurance. If an application frequently writes a large amount of transient data to the disk, it will not only severely shorten the service life of the mobile phone motherboard, but also leave residual data fragments in the unallocated cluster space of the disk that are difficult to completely erase. This software strictly implements the "zero high-frequency Flash writing" design principle at the system architecture level:
  ▶ (1) All real-time high frame rate image data streams output by the screen capture pipeline are strictly limited to the flow in the RAM physical memory mapping ring buffer. After completing the OpenCV feature comparison, the destructive release is directly performed in the memory, and will never go through the old disk transfer mode of "screen capture - save to disk file - then read from disk - delete after determination";

14. Cross-platform operating environment (PRoot Linux) internal file system and system call interception data privacy protocol
14.1 [PRoot user space virtualization and file system mapping privacy boundary]
This software pioneered the integration of an embedded lightweight Ubuntu Linux container environment based on PRoot technology on the Android mobile terminal. In order to make the Python automation engine and C/C++ dynamic link library run normally, PRoot uses the Linux ptrace tracking mechanism to dynamically virtual map and redirect the file system path at the user space layer. The Maintainers disclosed the following about the internal data privacy mechanism of the virtual file system:
  ▶ (1) Physical isolation of the virtual root directory: The virtual root directory (/) in the container strictly corresponds to a specific subdirectory under the application's private data directory (/data/data/com.azurpilot.ghio/files/rootfs/) in the host Android system. All file creation, editing, and compilation operations that occur within the container are physically completely limited to the sandbox quota allocated by the host, and there is absolutely no ability to break through this directory and perform unauthorized reading and writing to the Android system root directory (/system, /vendor, /data/system);
  ▶ (2) Host storage restricted mount (Bind Mount): In order to realize import and export configuration and log sharing, this software only uses the -b binding mount parameter of PRoot to mount the host application-specific private data directory and the public download directory explicitly authorized by the user into the container. This software will never forcibly mount the DCIM album directory containing the user's private photos, the WeChat chat storage directory, and the system core sensitive directory into the container. It prevents the container environment from traversing the device's global privacy files from the source of the architecture.
14.2 [Information desensitization and forgery mechanism of virtual /proc and /sys nodes]
In a standard Linux system, the /proc and /sys virtual file systems directly expose the real device information of the underlying hardware, CPU serial number, kernel parameters, physical network card MAC address, and the complete command line parameters (cmdline) and environment variables (environ) of all running processes in the system. In the Android system, if ordinary applications can read the above nodes at will, it will seriously endanger the running privacy of other background applications. To this end, this software deploys a highly secure virtual node forgery and desensitization mechanism in the PRoot runtime:
  ▶ (1) Device feature forgery: The /proc/cpuinfo and /proc/version nodes read inside the container have all gone through PRoot’s local static simulation or desensitization filtering, and the underlying physical registers containing the real hardware serial numbers are not read;
▶ (2) Absolute isolation of process list: When processes running in the PRoot container (such as Python interpreter, Bash terminal) try to execute ps or read /proc, they can only observe the child processes inside the container derived from PRoot. It is physically impossible to detect the existence of third-party host processes such as WeChat, online banking, and games running in the foreground of the Android operating system, ensuring absolute isolation of the running status between different applications.
14.3 [Unprivileged execution and user identity mapping (UID 0 virtualization)]
Inside the PRoot container, the terminal prompt is usually displayed as root (UID 0). This is to meet the format requirements of the Ubuntu package management system (such as apt, dpkg) for privileged identities when installing compilation dependencies. The Maintainers hereby analyzes extremely important computer security principles to users:
  ▶ (1) The essence of virtual Root is non-privileged execution: the root identity displayed inside PRoot is purely a "fake root" based on ptrace. When all behaviors of this virtual root identity are mapped back to the Android Linux kernel, its actual effective user identity (EUID) is always and uniquely strictly limited to the ordinary unprivileged application identity assigned by the host (such as u0_a1234);
  ▶ (2) It is absolutely impossible to harm the bottom layer of the system: the virtual root identity cannot physically modify any files in the Android system partition, cannot turn off SELinux mandatory protection, and cannot read the system encryption certificate storage area. Therefore, the operation of the container environment will never provide an attack springboard for malicious programs to implement system-level evasion of privileges on the device.
14.4 [Life cycle security of temporary files and sockets in containers]
During the execution of the automated task, the Python process in the container will perform high-speed inter-process communication with the local loopback socket through standard Unix Domain Socket (UDS), and generate a temporary socket handle file in the /tmp directory of the container. This software deploys a strict exit cleaning daemon hook: every time the task is stopped or the host application exits, the daemon will automatically execute the unlink command to erase all temporary files and IPC pipes in the /tmp directory to prevent remaining socket files from being sniffed or reused by other malicious processes on the device.
14.5 [Supply chain privacy review of third-party Linux open source software packages]
The basic components of the Rootfs image file included with this software are directly extracted from the standard basic root file system package (Ubuntu Base Rootfs) released by the official Ubuntu LTS long-term support version, and are standardized and arranged through automated Docker containers in the CI build pipeline. The Maintainers strictly controls the security of the software supply chain: in the entire process of making images, they will never introduce any unsigned third-party PPA software sources of unknown origin, and never compile any closed-source black box binary components to ensure that every line of code in the entire Linux operating environment has traceable open source compliance.
14.6 [Data flow isolation of container network protocol stack]
The PRoot container does not have an independent network virtualization namespace (Network Namespace), and its network calls are entirely issued by the Linux network stack of the host Android system. This means:
  ▶ (1) Network permissions are completely inherited from the host: any network requests inside the container are strictly limited by the INTERNET permission status granted by the Android system to the host application. If the user cuts off the "mobile network and Wi-Fi access rights" of this software in the system settings, the Python script inside the container will instantly lose all networking capabilities;
  ▶ (2) Unprivileged network external connection capability: The container environment is absolutely unable to bypass the system’s firewall configuration to establish a secret communication channel to any unauthorized node.
14.7 [Sandbox consistency in multi-user and clone environments]
In some customized Android systems that support "Mobile Phone Clone", "App Dual Open", and "Work Profile", the operating system will assign different Linux user identifiers (such as UserId 10, UserId 999) to different clone environments. This software can perfectly adapt to the multi-user isolation architecture: when this software is run in a clone environment, its PRoot container file system is completely created in the clone's exclusive independent storage sandbox, and is completely physically isolated from the data in the main user environment at the bottom of the file system. The configurations and logs of the two are not connected to each other, completely eliminating data concatenation and cross-contamination in a multi-account environment.
14.8 [Runtime integrity self-check and anti-tampering mechanism]
To prevent malware from locally tampering with critical Python automation scripts within the PRoot container or planting phishing pages, the software performs a SHA-256 hash integrity self-check of critical files before each startup. Once it is detected that the core automation logic script has been illegally tampered with by the outside, the software will refuse to start and pop up a security warning, prompting the user to perform reinstallation and repair, thereby safeguarding the authenticity and purity of the user's local data processing logic.

15. Image recognition template matching and deep learning neural network model local inference data flow full link review
15.1 [Topology of computer vision data flow in local memory]
The software's core visual perception system relies on a highly optimized native computer vision pipeline. In order to eliminate doubts about whether images will be peeked by the cloud background, the Maintainers conducted a panoramic public review of the entire life cycle memory flow path of screenshot image data from generation to destruction:
  ▶ (1) Pixel collection source: Create a virtual Surface through the Android MediaProjection interface, and the hardware graphics synthesizer copies the rendering pixels of the physical screen to the GraphicBuffer physical memory page allocated by the system;
  ▶ (2) Zero-copy Native mapping: The Native bridge layer dynamic library obtains the latest image frame handle through the AImageReader_acquireLatestImage API of libandroid.so, and directly accesses the RGBA_8888 pixel matrix to the C++ computing space through the direct memory mapping pointer (Direct Pointer), without generating additional intermediate copies in the whole process;
  ▶ (3) Color space conversion and matrix slicing: The OpenCV algorithm library calls cv::cvtColor to convert the RGBA matrix into a grayscale image (GRAY) or a three-channel BGR matrix for template matching, and perform rectangular cropping based on the screen-specific ROI region of interest (Region of Interest) that the current task focuses on;
  ▶ (4) Algorithm comparison and immediate release: After the feature matching algorithm completes the calculation of the cross-correlation coefficient matrix in the memory, OpenCV's cv::Mat smart pointer reference count returns to zero, and the underlying image pixel memory area is immediately destructed and released and marked as reusable. Its survival period usually only lasts a few milliseconds to more than ten milliseconds;
  ▶ (5) Absolutely no outgoing pipeline: In the above-mentioned full link, the code absolutely does not contain any logic for sending the image buffer to the external network through network protocols such as Socket, HTTP, FTP, etc. The life and death of the image pixel matrix are completely locked in the single-machine RAM hardware chip.
15.2 [LiteRT neural network lightweight model inference privacy security]
This software integrates the LiteRT (formerly TensorFlow Lite) end-side lightweight machine learning inference framework developed by Google and is used to perform optical character recognition (OCR). The Maintainers explains the operating characteristics of the deep learning model as follows:
  ▶ (1) Local offline storage of model files: The neural network weight model files (.tflite format) used for text detection and recognition are packaged and distributed offline along with the software installation package in the form of read-only assets (stored in the assets/ directory). When this software performs text reasoning, it loads the model file completely through the local CPU or GPU hardware accelerator, and there is absolutely no need to upload any image slices to any external cloud AI interface (such as the public cloud OCR API of major cloud vendors);
▶ (2) Instant memory overwriting of input and output feature tensors: When the neural network performs derivation, the input image tensor (Tensor) and the output character probability distribution matrix, after the inference function completes the forward propagation (Forward Pass) and is decoded into the final UTF-8 text, the tensor memory buffer is immediately released by the allocator of the framework, without retaining any historical latent space feature vectors of the original picture that can be reversibly deduced;
  ▶ (3) The model does not have continuous learning and backpropagation: The LiteRT model built into this software is a pre-trained and solidified offline inference model. It only performs forward derivation on the user device and absolutely does not perform any local backpropagation training. Therefore, there is no technical possibility of integrating the user's personal game screen into the neural network weights and leaking them.
15.3 [Screen watermark, anti-screenshot and sensitive application window avoidance]
In daily use of mobile devices, users inevitably need to open applications involving property privacy (such as mobile banking, password safes, personal income tax, etc.). The Maintainers clearly informs the software of the respect mechanism for system sensitive windows:
  ▶ (1) FLAG_SECURE hardware security window circumvention: When the user opens a high-security application that declares the WindowManager.LayoutParams.FLAG_SECURE flag in the foreground (such as online banking password input interface, encrypted communication software private chat interface), the SurfaceFlinger synthesizer at the bottom of the Android operating system will protect the window at the hardware level. The area of the image captured by this software through MediaProjection will be directly forcibly replaced by the system with pure black pixels (Black Out), this software is physically unable to intercept any real pixels of the protected window;
  ▶ (2) Natural physical isolation of independent virtual screens: When the user adopts privileged mode to run the game on the second virtual screen, the rendering layer stack of the virtual screen and the main physical screen belong to a completely different window context. All private operations of the user on the home screen, such as WeChat chat, photo browsing, and web browsing, do not overlap with the virtual screen at the operating system layer level. The image acquisition pipeline of the virtual screen is completely invisible to any private images of the user's home screen, building the strongest physical display isolation line of defense.
15.4 [Transparent auditability of abnormal deadlock screenshots and troubleshooting]
As mentioned above, when extreme technical failures such as interface deadlock or continuous matching timeout occur, the system may save a frame of the scene at the moment of the failure to the local debug/temporary directory. In order to ensure the absolute transparency of this mechanism, the Maintainers has made the following compliance protection design:
  ▶ (1) The saving behavior is completely controlled by the user: The user can independently find the switch for "Allow error screenshots to be saved" in the "Advanced and Debugging" panel in the software settings, and the user can turn it off completely at any time. After shutting down, even if the system encounters continuous deadlock errors, it will never save any frame of pictures on the physical disk;
▶ (2) The screenshot saving path is completely public: All troubleshooting screenshots are stored in a private path within the device's application in an open and transparent standard PNG format. Users can preview one by one at any time through the built-in log management panel, select all, and immediately and completely delete them physically with one click;
  ▶ (3) Never automatically and silently upload: The saved screenshots are only for the user's personal visual inspection and troubleshooting locally, or they can be submitted to the community for help after the user is deeply desensitized. This software will never silently package these screenshots in the background and send them back to any external address at regular intervals.
15.5 [Safe storage of user-defined template libraries and image features]
Some advanced users took advantage of the advanced customization capabilities of the upstream AzurPilot framework to cut and upload their own personalized game interface template feature maps (Custom Assets) through the WebUI. Users are informed: All image resources uploaded or imported by users are saved in the corresponding assets directory of the local PRoot container. This software strictly treats it as the user's private assets for local storage protection, and will never transmit the user's private templates back to the public warehouse without the user's authorization.
15.6 [Screen pixel grayscale and feature hash dimensionality reduction]
In order to further compress the memory footprint and improve processing security, the image engine performs grayscale and Gaussian blur dimensionality reduction on the original color pixels in many scenarios, and only extracts edge contours (Canny Edge) and feature hash (pHash). 16. Embedded WebUI, WebSocket gateway and local IPC communication security protection system
16.1 [Local Web Console Network Topology and Security Protection Positioning]
This software integrates a local WebUI interactive console built on a modern front-end framework, and a back-end RESTful and WebSocket API gateway built on the Python aiohttp / FastAPI architecture. This web architecture is designed to provide users with a modern touch-enabled configuration interaction interface on a mobile device screen. The Maintainers discloses the following about system internal communication security and data privacy:
  ▶ (1) Default loopback network closed-loop binding (127.0.0.1): Under the default security configuration, the web daemon built into this software is strictly configured to only listen on the local loopback network interface (Loopback Interface, 127.0.0.1:25548). This network interface is a set of pure software virtual network layers inside the operating system kernel. All TCP messages and WebSocket data frames generated by it are directly short-circuited and forwarded only in the physical memory of the device, without going through the physical network card chip (Wi-Fi or cellular antenna) outside the device at all. This means that any other device on the external LAN or public network cannot physically detect the existence of this port, and absolutely cannot send any network packets to this loopback port;
  ▶ (2) Double identity authentication firewall (Token-Based Authentication): In order to prevent other malicious third-party applications installed on the device from using the same LAN loopback authority to call the control interface without authorization, this software has designed an extremely strict identity authentication system. All HTTP resource requests and WebSocket handshake establishment requests initiated to the WebUI gateway must carry a valid security token with high entropy value (X-Api-Token / Authorization Bearer Token) in the request header or pass encrypted Session Cookie verification. Any illegal request that does not carry a valid Token will be forcibly rejected by the gateway with an HTTP 401 Unauthorized status code during the handshake phase.
16.2 [Tight defense against cross-site request forgery (CSRF) and cross-domain resource sharing (CORS)]
In the mobile Internet environment, malicious web pages may try to induce users to open a specific phishing page in the browser, and use the JavaScript script of the page to send illegal cross-domain asynchronous requests to the local loopback address (http://127.0.0.1:...) in an attempt to steal local configuration or control software. In order to completely block such high-risk network vulnerabilities, this software deploys a bank-level cross-domain defense strategy on the web back-end gateway:
▶ (1) Strict Origin and Referer source verification: The gateway will closely examine the Origin request header of each incoming request, and only allow access requests from the internal WebView component of the software (such as specific Android internal protocol headers) or trusted domain names explicitly configured by the user;
  ▶ (2) Cross-domain sharing of credentials is prohibited: The gateway forcibly turns off Access-Control-Allow-Origin wildcard support for untrusted domain names, and browsers are strictly prohibited from passing sensitive identity credentials in cross-domain scenarios;
  ▶ (3) WebSocket handshake source blocking: When establishing a two-way WebSocket connection for real-time log streaming and status push, the gateway will strictly compare the source address of the handshake message and completely intercept illegal WebSocket hijacking connections (CSWSH attacks) initiated by external malicious websites.
16.3 [Local inter-process communication (IPC) mechanism and data security channel]
This software is composed of two independent running entities, the Android native host application process (Kotlin) and the Python automation process inside the PRoot container. Local communication between the two layers uses a highly isolated and trusted IPC data channel:
  ▶ (1) Standard input and output pipe guard (Stdin/Stdout Pipe): The host process sends keep-alive pulses and life cycle termination signals to the child process through the underlying standard POSIX pipe. The pipe is strictly protected by the Linux process tree permissions, and external unauthorized processes cannot intercept the pipe content;
  ▶ (2) Local loopback private protocol encrypted transfer: The front-end control instructions of the host application and the execution status report of the sub-process are restrictedly transmitted in the 127.0.0.1 loopback network through the internal customized JSON-RPC protocol. The transmitted data structure is strictly limited to task state enumeration (such as TaskState.RUNNING), current execution round count, and error text description, and never contains any system-level sensitive data or user real identity privacy.
16.4 [WebUI front-end local static resource security review]
The web page front-end static resources embedded within this software (including HTML skeleton, CSS style sheets, compiled JavaScript packaged products, font libraries and SVG icons) are all built into local storage in the form of offline static assets along with the software installation package. When the user uses the WebView interface that comes with this software to operate:
  ▶ (1) Pure offline loading and zero external CDN script dependency: All JS libraries (such as front-end framework codes such as Vue/React/Tailwind) are loaded and parsed directly from the local disk of the device, and any third-party external scripts that may be tampered by middlemen or have tracking codes are never dynamically loaded remotely from external commercial CDN acceleration nodes;
▶ (2) Content Security Policy (CSP) protection: The web page deploys strict CSP response header rules, which prohibits the page from dynamically executing any inline scripts without hash verification (unsafe-inline), prohibits loading images from external untrusted domain names or initiating asynchronous requests, and comprehensively resists cross-site scripting attacks (XSS).
16.5 [Transmission encryption and anti-brute force cracking in LAN open control mode]
When the user actively turns on "LAN Control" in the software settings according to their own management needs and binds the monitoring to 0.0.0.0, the software automatically improves the security defense level:
  ▶ (1) IP access frequency limit (Rate Limiting): The gateway has a built-in request limiter based on the memory leaky bucket algorithm, which implements strict frequency limits on unauthorized test requests from the same LAN IP address. Once it is detected that a specific IP fails token password authentication more than 5 times within 1 minute, the system will automatically blacklist the LAN IP and block it for 15 to 60 minutes, fundamentally defeating brute-force attacks carried out by hackers using password dictionaries;

21. In-depth guide on personal information security life cycle audit, de-identified hash transfer and terminal defense
21.1 [Closed-loop data life cycle security audit]
In accordance with the national industry standards for data security governance, this software subdivides the local processing process of personal information on mobile devices into six complete stages: "Generation - Collection - Transmission - Storage - Use - Destruction", and builds solid cryptography and engineering technical defense barriers in each independent stage:
  ▶ (1) Generation and collection stage: Strictly abide by the principle of explicit authorization by the user, do not collect without authorization, and do not activate screen projection and input channels in non-running state;
  ▶ (2) Transmission stage: All inter-process communication (IPC) and internal data transfer within the container are limited to the internal virtual bus of the local system, and the entire network remote access uses TLS 1.3/SSH-2 industry-high-strength encrypted tunnels;
  ▶ (3) Storage stage: 100% data is enclosed within the Linux private sandbox, and sensitive keys are excluded from system cloud backup;
  ▶ (4) Usage stage: real-time calculation of memory data, and never build any business portrait or statistical model that goes against the user’s original intention;
  ▶ (5) Destruction phase: Log rotation is automatically cleaned, temporary images are destroyed upon exit, and physical sectors are completely erased when the application is uninstalled.
21.2 [Practice of de-identified hash algorithm in data diagnosis]
In order to protect users' digital personality and privacy rights to the greatest extent when reporting complex technical failures to the open source community, this software introduces a one-way de-identification mechanism based on the SHA-256 cryptographic hash function when generating internal diagnostic snapshots. The system automatically converts some occasional device internal identifiers into irreversible fixed-length hash digests (such as hash("device_id_salt") -> a1b2c3d4...). This summary is only used as a temporary symbol to distinguish different test devices. No external organization can use this hash summary to reversely deduce the user's real hardware parameters or personal identity.
21.3 [Tightened access permissions for cross-process shared memory (Shared Memory)]
When transferring large-capacity screen frame images between the Native bridging layer and the Java/Kotlin host layer, this software uses the Android underlying standard ashmem (Android Shared Memory) or Linux memfd anonymous file handle. The Maintainers has set extremely strict protection flags on this shared memory handle at the bottom of the code:
  ▶ (1) Only the host application process and its legally derived privileged app_process child processes are allowed to pass the file descriptor (File Descriptor, FD) through Binder IPC;
  ▶ (2) The memory area is set to read-only (PROT_READ) sharing to prevent the child process from accidentally tampering with the original graphics data;
  ▶ (3) Any external third-party malicious process that does not hold a legitimate Binder token is prohibited from mapping the shared memory segment at the operating system kernel level, effectively safeguarding the memory-level confidentiality of the pixel stream.
21.4 [Defense mechanism against Side-Channel Attack]
Under an extremely high-confrontation security threat model, hacker software may try to infer whether specific changes have occurred on the current game screen by monitoring the device's CPU instantaneous power consumption curve, cache miss rate (Cache Miss Rate), or the timing difference broadcast by a specific system (the so-called microarchitectural side-channel attack). The state machine engine of this software introduces smooth buffering and dummy operation filling (Dummy Operation) in the time dimension into the scheduling algorithm, so that the CPU load of the overall computing task presents a smooth and even distribution, which greatly increases the signal-to-noise ratio and cracking difficulty of external side channel analysis.
