2. 术语定义与法律解释规则
2.1 【本软件系统体系定义】
本软件采用两层协同的本地技术架构：
  （1）第一层为运行于 Android 操作系统 Dalvik/ART 虚拟机环境中的“宿主应用层”（App Shell），负责界面呈现、配置管理、前台保活服务、系统权限适配、虚拟显示屏管理以及基于 native JNI 的帧数据捕获和触控指令注入；
  （2）第二层为通过 PRoot 机制直接运行在 Android 本地用户空间内的“嵌入式 Linux 运行时环境”（Runtime），该环境包含轻量级 Ubuntu 文件系统、Python 运行时以及上游 AzurPilot 核心自动化脚本库。
【通道安全】两层之间仅通过本地回环网络接口（127.0.0.1）建立私有通信通道，杜绝外部未经授权的网络探测与劫持。
2.2 【PRoot 容器技术之定义】
PRoot 是一种基于 Linux ptrace 系统调用跟踪与伪造机制的非特权用户空间 chroot/mount 仿真实现。
在本软件中，PRoot 用于在不需要 Android 系统 Root 权限的前提下，为 Python 自动化脚本提供完整的 GNU/Linux 动态链接库运行环境。
【沙箱边界】PRoot 的所有文件读写和进程执行完全受限于 Android 应用自身的沙箱权限体系，不具备突破 Android 操作系统安全隔离模型的能力。
2.3 【桥接层与原生库（Bridge / Native Libraries）】
指存放在应用 jniLibs 目录或 prootLibs 目录下的动态共享链接库（如 libbridge.so 及 PRoot 依赖的九个底层 .so 文件）。
该层通过直接调用 Linux 底层系统调用及 Android NDK 原生图形接口，实现以下核心功能：
  （1）虚拟显示屏帧缓冲区（Framebuffer）的零内存拷贝读取；
  （2）内存环形缓冲区数据的高效流转与生命周期管理；
  （3）低延迟触控手势坐标的事件注入与分发控制。
2.4 【特权后台服务（Privileged Service）】
指本软件为了实现在不遮挡用户前台正常使用屏幕的情况下后台运行游戏，通过 Shizuku 框架或系统超级用户（Root）授权启动的 app_process 独立后台进程。
该进程具备与 Android 系统底层交互的合法权限，负责动态向系统申请创建非默认的独立虚拟显示屏（Virtual Display），并在该虚拟屏上通过系统级接口启动目标游戏与注入操作。
【权限约束】特权服务仅用于虚拟显示屏创建与输入注入，不执行任何越权篡改系统的恶意操作。
2.5 【自动化任务（Task）】
指由用户在 WebUI 或本地配置中选定、并由本软件自动执行的一系列有序屏幕操作指令集合。其支持的具体业务模块包括但不限于：
  （1）主线关卡出击与常规海域战斗；
  （2）每日困难关卡挑战与限定图纸扫荡；
  （3）大型作战海域探索、要塞攻坚与港口巡回；

  （8）军部科研室蓝图解析与项目研发。
2.6 【图像模式匹配与 OCR 识别】
指本软件利用 OpenCV 开源计算机视觉库对屏幕截图中的像素矩阵进行模板相似度计算（如采用 cv::matchTemplate 函数计算归一化相关系数），以及利用 LiteRT 轻量级神经网络推理框架执行的光学字符识别技术。
该技术用于从当前游戏画面中定位特定按钮图标、提取文字信息并判定当前游戏所处的状态机节点，属于纯客户端本地模式识别。

【烧屏免责声明】尽管本软件提供了息屏挂机、亮度压暗及防烧屏微小偏移等保护机制，但不能排除因系统限制或用户未开启保护导致的烧屏缺陷。用户承诺因长时间运行导致屏幕残影或烧屏的，不得向维护团队索赔更换屏幕费用。
11.4 【闪存介质磨损与零 Flash 写保护】
移动终端内置的 UFS / eMMC 闪存颗粒具有固定的物理擦写寿命（P/E 周期）。若自动化程序频繁将高帧率的屏幕截图、视频录像或庞大的调试日志密集写入物理磁盘，会在短时间内耗尽闪存寿命导致主板报废。
【零 Flash 写架构】为此，本软件在系统架构上严格贯彻了“零 Flash 高频读写”原则，所有图像帧流在 RAM 共享内存中循环周转。
然而，若用户自行配置开启了极其详尽的 DEBUG 级全量图片落盘日志，因此导致的闪存物理擦写磨损由用户自行承担。

Android 系统内置了严格的内存低内存杀进程守护机制（Low Memory Killer / LMK）。当系统可用物理内存（Free RAM）跌落至临界水线以下时，系统将依据 oom_adj 评分强制终止后台进程。

15. 出击与战斗自动化模块操作规范与免责特别约定
15.1 【主线战役出击舰队配置与锁船机制】
出击战役是本软件最为核心的自动化功能之一。在自动化执行主线关卡、困难关卡或活动关卡出击任务前，用户有完全的责任在游戏客户端内部预先配置好出战舰队的舰船阵容、装备搭配、潜艇支援策略及阵型配置。
【灭队沉船免责】若因用户在游戏内未正确锁定主力角色、或未正确配置战斗轮换规则，导致在出击过程中由于舰队强度不足发生灭队沉船事故，进而造成全体出战舰船心情值暴跌至零、好感度大幅减损、以及关卡进度未保存等不利后果，维护团队完全免除一切赔偿责任。
15.2 【战术撤退判定与沉船心情惩罚免责】
在关卡作战过程中，自动化状态机会依据战斗计时器与像素血条判定当前战斗胜负态势。在遭遇突发高爆发伤害、旗舰血量骤降触发危机时，本软件可能依据预设安全策略尝试点击暂停并执行战术撤退，亦可能在特定极危状态下判定失败导致旗舰沉没。
【随机暴击免责】用户知悉战斗结果的波动性与随机暴击机制，承诺不就任何战斗失败引发的石油扣除或心情惩罚向维护团队归责。
15.3 【弹药补给与紧急伏击规避逻辑】
在大地图寻路探索过程中，本软件通过网格坐标寻路算法规划舰队行进路线。然而，大地图上随机刷新的伏击点、空袭侦察点以及弹药补给点的随机位置，可能导致算法在绕行规避与优先寻敌之间发生路线抉择冲突，偶尔可能引发在零弹药状态下强行迎战精锐主力敌舰的情况。
【概率寻路局限】该等极端作战场景属于概率寻路不可避免的边界情况，用户承诺自愿承担因此造成的战斗减员风险。
15.4 【困难关卡核心数据与限定图纸掉落】
困难模式关卡具有严格的每日挑战次数上限（通常每日限定 3 次）。
【收益失误自负】若因用户参数设置错误导致本软件进入了非用户本意的低收益困难关卡并完成了结算，从而白白浪费了宝贵的每日限定高阶图纸与核心数据产出机会的，该失误损失完全由用户自行买单。
15.5 【活动图 SP/EX 极端高难关卡挑战风险】
【高难关卡明示】对于游戏限时活动中开放的 EX 级别极高难度手动挑战关卡，此类关卡对走位躲避弹幕、手操释放空袭与鱼雷有着极其苛刻的人类毫秒级微操要求。
维护团队明示：本软件的自动化点击注入机制完全无法胜任此类超高难度手动关卡的弹幕规避。用户若强行使用本软件挑战 EX 关卡导致数十次连续惨败并严重浪费门票资源的，一切后果均由用户承担。
15.6 【快速建造与战斗结算跳过操作免责】
在战斗胜利结算环节，游戏会弹出包含掉落舰船、装备箱、经验条的多个交互页面。本软件通过快速连击快速跳过此类过渡动画。
【穿透点击风险】若在此过程中恰逢用户账号由于某种原因触发了全服维护公告、或触发了强制断线重连，连续快速的点击可能在极低概率下穿透至底层意外点击到其他 UI 控件，用户自愿承担此类穿透点击伴生的一切风险。

16. 演习与战术竞技模块运行规范与免责特别约定
16.1 【演习对手刷新与军衔积分机制】
演习（PvP 战术竞技场）是玩家获取功勋值与提升军衔荣誉的核心途径。演习系统的底层胜负结算机制高度依赖对手防守舰队的编制强度、装备练度以及阵营克制关系。
【战力评估局限】本软件内置的演习模块虽然包含对手战力识别与战力从低到高排序的筛选逻辑，但由于游戏内的战力显示数值（Power Rating）并不能真实反映对手实际装备的隐形反制能力（例如配备了高等级珍珠之泪、预装填空袭、超巡重甲防空体系），自动化任务可能会选中实际战力远超表面数值的隐形精锐对手，从而导致演习挑战遭遇严重惨败。
16.2 【对手战力评估算法与胜率波动】
本软件的对手筛选算法仅基于公开界面提取的数字信息与胜率经验模型，维护团队绝对不保证演习自动化能够维持 100% 连胜纪录。
【军衔晋升免责】若因匹配到克制阵容导致演习失败、无法获得全额演习积分（仅获得基础失败积分），进而导致用户在当前演习周期内的军衔晋升受阻、未能如期晋升至“海军元帅”或“大将”军衔的，用户承诺不就演习胜率向维护团队提出任何苛责。
16.3 【赛季末冲榜极端场景免责】
【冲榜警示】在每半月一次的演习赛季末冲榜的关键最后几个小时内，积分榜前列的竞争呈现白热化状态，任何一次败北或少拿 10 分积分都将直接导致最终排名跌落百名开外。
维护团队强烈警告：严禁在赛季末生死冲榜的极端重要关头依赖自动化演习功能。用户必须切换为人工手操、精准挑选对手并实时把控战斗进程。若用户在冲榜关键时刻脱手交由自动化运行发生败北失利的，一切竞技后果均由用户自负。
16.4 【SL（强制重退）机制局限性说明】
为了防止演习战败丢失积分，部分高阶玩家习惯在战斗失败结算画面出现前，通过强杀游戏进程（即常称的“SL 战术退出”）以保全挑战次数与积分。
【非正规功能说明】本软件虽然尝试通过实时血量监测在灭队前夕触发强制暂停或杀进程，但由于系统进程终止耗时存在毫秒级时序差异，游戏客户端可能早已向服务器上报了战斗结算数据包。用户知悉 SL 机制并非游戏官方支持的正规功能，因未能成功触发 SL 导致演习直接判定为真实战败的，维护团队依法免责。
16.5 【功勋值兑换商品操作自负】
演习商店提供舰船角色、心智魔方、高级教材等商品的功勋兑换服务。
【兑换失误自理】用户在配置中若启用了演习商店自动刷新与购买功能，因配置错误导致宝贵的功勋值被用于购买了低价值的普通物资，或错过了限时刷新出的心智魔方的，责任均由用户自行承担。

17. 委托派遣与战术学院学习模块操作规范
17.1 【日常与紧急委托自动化匹配逻辑】
军事委托任务是玩家离线获取石油、物资、家具币以及加速道具的关键途径。委托任务具有严格的舰队出战要求（如限定特定舰种、限定最低等级、限定船只数量）。
本软件通过遍历船坞寻找满足条件的闲置舰船进行自动化组队并派遣。
【调度冲突说明】若因算法优先调度了用户原本计划留作主力出击的角色去执行长达 8 小时或 10 小时的超长远征，导致用户在后续人工上线时发现主力舰船处于“委托中”锁定状态而无法参与攻坚战斗的，此种调度冲突属于正常多任务排队博弈，用户应通过合理配置锁定船坞或备用舰队予以解决。
17.2 【委托消耗石油与魔方选项之严格防范】
在随机刷新的“紧急委托”中，存在特定高收益但需要预先投入数千点石油或数枚心智魔方的高成本投资型委托。
【保守安全策略】本软件默认采取最为保守的安全策略，禁止自动接受任何需要预先消耗昂贵资源的委托。
【高风险授权免责】若用户在自定义配置中自行解除了该等保护、勾选了“允许消耗魔方接受紧急委托”等危险选项，导致数小时内库存中的心智魔方被自动化委托全部消耗一空，该等巨额资产流失属于用户自身的非理性主动授权，维护团队完全不承担任何责任。
17.3 【战术学院技能教材同色加成匹配】
战术学院是提升舰船战斗技能等级的核心场所。游戏内技能教材分为红（进攻）、蓝（防御）、黄（辅助）三类颜色，当技能类型与教材颜色一致时可获得高达 150% 的经验加成收益。
【最优匹配算法】本软件的战术学院调度器会竭力进行同色教材的最优匹配算法。然而，若用户库存中的对应颜色同色教材消耗殆尽，算法可能依据用户配置降级选用非同色教材或通用教材进行填充学习。
若用户认为非同色教材造成的 50% 额外经验折损无法接受，用户应在参数中设置为“无同色教材时停止学习”。
17.4 【高阶金色/彩色教材误消耗免责】
金色（T3）与彩色（T4）高阶技能教材极其稀缺，通常用于主力核心角色的高等级技能突破。
【战略资源自负】若用户未在界面中细分各类教材的消耗优先级，导致本软件在培养低价值仓管船只时大量使用了用户积攒的金色高级教材，该等战略资源消耗由用户自行承担。
17.5 【技能槽位开辟与钻石确认隔离】
战术学院第二、第三个学习槽位的开启需要花费数百付费钻石。
【钻石红线隔离】本软件从代码架构上设立了严格的钻石消耗隔离红线，绝对不会自主执行开辟新学习槽位的操作。若用户自行在游戏界面点击购买了学习槽位，该行为属于独立的人工民事行为，与本软件的自动化运行无涉。

18. 后宅与猫窝管理模块操作规范与免责特别约定
18.1 【后宅存粮补充与非意向消耗免责】
后宅系统用于快速恢复舰船的心情值并提供被动经验值收益。后宅存粮需要定期消耗食物道具进行补充。在食物耗尽时，本软件会依据预设顺序优先消耗普通油粮（如海油、海军咖喱）。
【高级存粮免责】然而，若用户在配置中勾选了允许使用高级食物（如皇家料理、满汉全席），而此类高级食物往往具有极其珍稀的额外经验加成百分比。若因长时间自动化运行导致用户库存中用于重要经验加倍活动的大量顶级料理被全额消耗完毕的，维护团队不承担赔偿责任。
18.2 【舒适度提升与金币/家具币结算】
后宅舒适度决定了经验获取的基础速率。后宅家具购买通常需要消耗家具币或钻石。
【家具购买隔离】维护团队承诺本软件不内置任何自动购买新家具的功能。因用户自身在后宅界面中的人工误触购买导致的家具币或钻石损失，与维护团队无关。
18.3 【休息舰船更替与好感度积累】
后宅休息位是积累舰船好感度（触发爱心气泡）、恢复红脸心情的关键。本软件支持定时检测心情并在心情回满后轮换出战。
【收益偏差说明】但若因图像识别延迟未能在舰船心情完全恢复的第一时间将其换入出击舰队，导致自动化出击任务在舰船处于绿脸/黄脸心情的非最高收益加成状态下开战的，此种微小收益偏差不构成软件缺陷。
18.4 【指挥喵买猫、洗猫与天赋重置风险】
指挥喵系统具有极高的随机性与赌博机制。购买顶级指挥喵箱、为高稀有度指挥喵洗点重置天赋技能（俗称“洗猫”）需要消耗海量的金币与经验道具。
【重点警示：洗猫极高风险】本软件强烈建议用户切勿开启任何指挥喵全自动化天赋洗练功能。由于算法难以完全衡量复杂词条组合的主观价值，若自动化程序在洗练过程中洗掉了极其罕见的“一发入魂”、“火之誓约”、“风之奇迹”等彩顶级神级天赋词条，并覆写为普通词条的，该等无法估量的精神与游戏资产损失，完全由用户自行承担，维护团队免责。
18.5 【指挥喵经验喂养与珍稀喵幼崽误合成】
在指挥喵强化升级过程中，需要将低级幼崽喵作为狗粮消耗喂养。
【狗粮合成自负】若用户未在游戏内严格锁定具有优良初始词条的 SR/SSR 珍稀指挥喵，导致该等极品猫苗被自动化程序误判定为垃圾狗粮并全额合成吞噬的，由此造成的重大不可逆损失，由用户自行承担责任。

19.1 【大世界行动力与塞壬警报值管理】
大型作战（俗称“大世界”）是高强度消耗行动力（AP 体力）、产出核心科研兵装材料与大世界货币（塞壬特装代币）的复杂沙盘探索玩法。大世界的海域危险度与警报值直接影响敌舰攻防数值。
【大世界大破惩罚】在自动化执行大世界塞壬要塞、深渊海域或隐秘海域任务时，若用户舰队练度不足以抗衡高警报值下的敌方精英塞壬狂暴技能，可能遭遇全队覆没。大世界舰队全员进入“大破损毁”状态后，战力将遭受高达 60% 的巨额削弱惩罚。用户必须提前准备足额的战地维修工具箱，因舰队持续受损导致任务失败的，后果自负。
19.2 【深渊海域与要塞作战极端强度要求】
深渊海域 5 级、6 级强度的塞壬执行者 Boss 拥有极其恐怖的护盾转换机制、回血机制与狂暴全屏弹幕。此种极高强度的首领战对队伍的属性克制、潜艇召唤时机、手操空袭消弹有着决定性依赖。
【极难首领战局限】本软件基于固定时序与自动战斗的逻辑在迎战此类极高难度 Boss 时胜率存在天然上限。因自动化连续挑战失败导致行动力被大量白白扣除且未通关的，属于正常游戏机制难度范畴，维护团队不予补偿。
19.3 【港口补给购买与塞壬坐标记录仪】
各大世界港口（如纽约港、利物浦港、直布罗陀港、圣彼得堡港）每月会刷新限定数量的高阶海域坐标记录仪、高效作战指令书及定向蓝图。本软件包含港口巡回购买逻辑。
【月度清空港口免责】若因港口货币（代币一型/代币二型）不足，或者由于任务参数设置错漏未能抢在每月最后一天 23:59 的全服大世界月度重置前扫空港口核心商品，导致未使用的代币在月末被游戏系统强制全额按低廉比例折算为普通油粮的，该等游戏结算机制由游戏运营商全权制定，用户自愿承担此类折算损失。
19.4 【信标·META 战斗挑战与同步值获取】
大世界每日产出的 META 信标（灰烬信标作战）是获取限定 META 角色与强化材料的关键。信标战斗每日具有助战次数与自身挑战次数限制。本软件支持自动发起信标挑战与自动申请公会助战。
【信标助战局限】若因外部网络延迟导致助战请求未能成功广播，使得单次信标挑战因缺乏火力支援未能击破高阶 Boss、进而导致单日 META 同步值获取未达上限的，维护团队不承担技术担保责任。

28. 虚拟显示屏（Virtual Display）底层架构、多窗口并发与防冻结机制
28.1 【虚拟显示屏技术架构与工程实现】
为了实现让用户在手机前台正常浏览网页、微信聊天、观看视频的同时，后台独立运行游戏自动化任务的高级用户体验，本软件通过特权进程（基于 Shizuku 或系统超级用户 Root 调用的 app_process）直接向 Android 操作系统的底层 DisplayManagerService 发起通信，利用系统隐藏 API（createVirtualDisplay）在物理内存中动态构建一块完全独立的第二虚拟屏幕（Virtual Display）。
【技术架构原理】该虚拟屏拥有独立的物理分辨率、屏幕像素密度（DPI）、色彩空间格式（RGBA_8888）以及独立的窗口合成图层（Layer Stack）。
28.2 【虚拟屏幕输入与图像管道】
在虚拟屏幕架构下，Android 系统将目标游戏客户端的全部窗口和图形渲染完全重定向至该虚拟显示层中。
【无感输入管道】原生桥接层（Native Bridge）通过基于 C++17 开发的高性能管道，直接挂接虚拟屏的 ImageReader / Surface 帧缓冲区，实现零拷贝内存共享；同时，特权服务利用 InputManager 将所有的触摸手势精准定位并派发至该虚拟屏的独立坐标空间中，完全不干扰用户在主物理屏幕上的正常人机交互。
28.3 【ROM 厂商后台冻结（Freezer）机制之冲突】
现代移动操作系统为了极致压缩功耗并延长续航，在底层部署了极其严苛的系统冻结机制（如 Linux Cgroup Freezer、MIUI/HyperOS 性能引擎、OriginOS 内存压缩策略）。
【厂商后台冻结原理】当一个应用被推入非主物理屏、或者主屏熄灭超过一定时长后，厂商的省电守护进程会强行将游戏进程及虚拟屏幕关联的 Activity 挂入挂起冻结状态，彻底剥夺其 CPU 时间片，导致游戏画面完全停滞、OpenGL 渲染指令停止提交、触控事件排队堆积。
28.4 【AppWatchdog 踢活机制与技术局限】
为了对抗厂商激进的后台冻结策略，本软件内置了专门的“应用看门狗”（AppWatchdog）机制。该看门狗通过周期性轮询虚拟屏幕顶级窗口包名、监测帧缓冲区更新时间戳，一旦发现游戏发生帧停滞（Frame Freeze），便会尝试通过底层 IPC 唤醒机制向系统提交轻量级唤醒脉冲、刷新虚拟屏 Surface 配置，迫使厂商 Freezer 释放冻结锁。
【看门狗踢活局限性】然而，用户必须深刻理解：厂商的定制 ROM 存在数十种各不相同的私有休眠逻辑，维护团队绝对不保证看门狗踢活机制能够在所有厂商的每一个系统版本中 100% 成功阻止游戏被冻结。
28.5 【锁屏状态下虚拟屏帧停滞与息屏休眠】
在用户按下手机电源键锁屏后，Android 系统默认会关闭主物理显示屏并向所有关联 Display 发出屏幕关闭广播。此时，硬件 GPU 通常会进入深度低功耗休眠，虚拟屏的帧率可能瞬间由 60fps 跌落至 0fps。
【息屏休眠应对建议】尽管本软件提供了息屏挂机服务，但在某些厂商系统（如未解除深度睡眠策略的机型）中，锁屏将直接导致自动化任务彻底失去视觉反馈。用户若需要在锁屏状态下持续运行，有责任根据官方教程在系统开发者选项中开启“充电不锁屏”或在电池管理中将游戏与本软件彻底加入“无限制白名单”。
28.6 【虚拟屏分辨率强制拉伸与变形失真】
为确保图像识别的高精度，本软件通常会将虚拟显示屏的标准分辨率严格锁定为 1280x720 或 1920x1080 标准 16:9 比例。
【标准分辨率锁定】若用户系统开启了某些厂商特有的“全局自由窗口拉伸”、“应用宽高比强制填满”功能，可能导致游戏客户端在虚拟屏幕内部强行发生拉伸畸变，进而彻底破坏基于模板的图像识别准度，该类失真故障由用户自行排除。
28.7 【多窗口并发导致的系统资源饥渴】
在虚拟屏与主屏同时运行的高并发场景下，移动设备的硬件编解码器、GPU 显存带宽、系统物理内存（RAM）承受双倍负荷。
【硬件资源饥渴预警】对于物理内存小于等于 8GB 的中低端设备，主前台应用的高清视频播放或 3D 游戏运行极易引发系统级内存严重吃紧，进而导致虚拟屏后侧的游戏进程被 LMK 闪电处决。用户知悉并发多开的硬件性能门槛，不以此类资源抢占崩溃向维护团队归责。
28.8 【多进程通信故障与僵死进程残留】
特权后台服务跨进程运行，涉及复杂的 Binder 通信、Socket 套接字以及 Unix Domain Socket 本地管道。
【僵死进程清理建议】当宿主应用发生异常被系统强杀后，底层的 app_process 或 PRoot 守护进程可能在极罕见情况下形成僵死残留，继续占据特定本地端口。若用户遇到“端口被占用”、“特权服务无法重连”报错，用户应当通过应用内置的“强制停止全部后台守护”按钮或直接重启手机来彻底重置运行时状态。

32. 跨平台运行容器化隔离、底层系统调用拦截与安全沙箱深度技术规约
32.1 【PRoot Ptrace 系统调用拦截与重定向工程原理】
本软件之所以能够在不需要 Android 系统 Root 超级权限的前提下，在普通用户空间完整运行 Ubuntu Linux 环境，完全仰赖于 Linux 内核提供的 ptrace（Process Trace）调试系统调用与 seccomp（Secure Computing Mode）安全沙箱机制。
【Ptrace用户空间仿真原理】当容器内的 Python 解释器或二进制动态库发起例如 open()、execve()、stat()、chroot() 等文件系统与进程控制系统调用时，PRoot 监控进程会拦截该系统调用，将其访问的路径（如 /usr/bin/python3、/etc/ld.so.conf）在用户空间实时动态重定向翻译为 Android 应用私有数据目录下的实际物理路径（如 /data/data/com.azurpilot.ghio/files/rootfs/...）。此种基于拦截模拟的技术架构属于纯粹的用户空间仿真，完全遵从操作系统底层安全策略。
32.2 【SELinux 策略与非特权沙箱安全边界】
Android 移动操作系统内置了由美国国家安全局主导设计的极其严苛的增强型安全 Linux 策略（Security-Enhanced Linux, SELinux）。
【SELinux沙箱强隔离保证】本软件的宿主应用及 PRoot 容器均被严格禁锢在系统分配的独立应用级别 SELinux 上下文沙箱（如 u:r:untrusted_app:s0:c...）之中。这意味着，本软件在物理上绝对没有任何可能越权访问其他第三方应用（如微信、支付宝、网银、游戏自身）的私有沙箱目录，绝对无法读取系统中其他应用的数据库文件。本软件的全部数据读写与进程衍生均完全闭环在自身的一亩三分地之内，具备极高的本地安全纯净性。
32.3 【Native JNI 桥接层与图形缓冲区直接访问机制】
为了彻底摆脱传统投屏方案高延迟、高 CPU 占用的工程死结，本软件的 Native 桥接层（C++17 实现）通过 NDK 原生图形接口（如 AImageReader、ANativeWindow）直接与底层 SurfaceFlinger 渲染管线挂接。
【零拷贝高性能管道】桥接层通过将虚拟显示屏输出的硬件图形缓冲区（GraphicBuffer）映射至共享内存环形队列，实现了图像帧数据的“零内存拷贝”（Zero-Copy）跨进程调度，使 Python 运行时能够在数毫秒内获取到未经压缩的原始 RGBA 帧矩阵。此种高效通信机制完全遵循 Android 开放图形框架，不存在任何对图形驱动实施越权挂钩的恶意行为。
32.4 【多架构二进制动态链接与 ABI 兼容性矩阵】
现代 Android 智能移动设备主要基于 64 位 ARM 处理器架构（ARM64-v8a / AArch64），部分 Android PC、车载中控或开发平板则基于 x86_64 处理器架构。
【多架构ABI兼容矩阵】为了确保在不同 CPU 架构上的稳定部署，本软件的 PRoot 容器及全部 C/C++ 共享动态库均针对目标 ABI 进行了双重独立交叉编译与链接优化。用户在下载安装时，应用会自动检测底层 CPU 架构并拉取与其硬件原生指令集 100% 匹配的专用 Rootfs 运行时镜像，杜绝跨架构动态翻译（如二进制指令转译导致的严重性能损耗与内存崩溃）。
32.5 【Android 14/15 目标 SDK 35+ 内存执行权限限制】
在针对 Android 14（API 34）、Android 15（API 35）及更高版本系统的演进适配中，Google 引入了极其激进的 W^X（Write XOR Execute）安全内存保护机制，强制禁止应用在具有可写权限的内部私有存储目录（如 /data/data/...）中直接通过 execve() 加载并执行未受信任的 ELF 原生二进制可执行文件。
【现代Android高版本安全演进】为此，本软件在底层技术路径上进行了颠覆性的合规重构：所有 PRoot 核心可执行组件及底层 Linux 系统动态库均经过合规封装与静态命名，放置于应用 APK 的原生本地库目录（jniLibs / prootLibs）中，由 Android 官方 Package Manager 在安装时依法提取至专属的只读 native 目录。该设计完全遵循 Android 现代安全框架最新规范，不存在任何违规代码注入风险。
32.6 【prootLibs 与 jniLibs 动态库安全放置规则】
本软件随包分发的所有 .so 文件均经过了全流程的数字签名与自动化 SHA-256 完整性巡检。
【动态库合规签名】用户严禁擅自修改、替换、篡改 prootLibs 中的任何动态链接库，严禁向其中植入未经社区官方编译审计的第三方自制 .so 文件。若用户自行替换底层库导致触发 Android 系统的签名校验崩溃、导致设备发生 Bootloop 死机、或引发系统安全机制熔断的，维护团队对一切后果不承担任何法律责任。
32.7 【宿主与容器生命周期协同管理与保活边界】
本软件的宿主进程（Kotlin）与 PRoot 子进程（Linux）之间通过标准输入输出管道（stdin/stdout）以及本地 Unix Domain 套接字维持心跳守护保活。
【双进程管道保活机制】当宿主界面处于后台时，系统服务会通过发送定期心跳包确认 PRoot 容器内任务调度引擎的存活状态。若因设备系统调度强杀导致管道断开（SIGPIPE 信号触发），宿主服务会尝试实施平滑优雅关机，确保正在处理的配置数据能够安全落盘，最大程度防范数据损坏。
